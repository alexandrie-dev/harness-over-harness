# Plan: HoH, первая версия — движок на Rust, настольное приложение, задачи

Статус: ждёт утверждения основателя. До утверждения код не пишется.
Решения основателя, на которых стоит план, записаны дословно в `plans/session-state.md`.
Факты об образцах — в `research/*.md`. Опись пакетов образца — в `docs/porting/MAP.tsv`.

## Goal

Сотрудник без навыков работы с ИИ одной кнопкой создаёт себе помощника под задачу своей компании
на локальной модели, а нам не приходится приезжать к заказчику и дописывать харнесс под каждую новую задачу.

## Non-goals

Этот план не делает:

- Перевод браузерного окна DeepSeek Harness (dsh) и его транспорта: `packages/client`, `api`, `typert`, `host`,
  `apps/web`, `apps/desktop*`. Окно пишем своё.
- Перевод `packages/experimental` (65 пакетов, 142 тыс. строк). Пакет оттуда берётся отдельным решением.
- Замену кода плагинов на лету, выражения `!!js` в конфигурации, установку плагинов через npm, исполнение
  чужих JavaScript-плагинов dsh.
- Исполнение программ модели в Node (`ptc-runtime`, `tool-executor-ptc`, `workflow*`): в Rust для этого нужен
  другой механизм, он проектируется отдельно после замера в бенчмарке.
- Чужие харнессы (Claude Code, Codex, Qwen Code и другие) внутри HoH — после первой версии.
- Почту и запись во внешние системы, общие задачи на отдел, площадку marketplace, версию для macOS,
  облачную модель как строителя задач — после первой версии.
- Защиту от враждебного кода сверх песочницы процессов, которая есть в dsh.
- Любые зависимости под GPL или AGPL.

### Этап 0. Основание и ядро

- `Cargo.toml` (workspace, `members = ["crates/*", "apps/*", "ui"]`, общий список зависимостей),
  `rust-toolchain.toml`, `.cargo/config.toml` (каталог сборки), `.gitignore`, `NOTICE` (уведомления MIT
  от DeepSeek Harness и Cordis).
- `docs/porting/PORTING.md` — правила переноса TypeScript → Rust: сервисы, события, эффекты, отмена,
  потоки, ошибки, конфигурация, тесты, запреты. `docs/porting/DEPS.md` — разрешённые библиотеки и лицензии.
- `docs/kernel.md` — описание ядра, которое пишет ведущий до кода.
- `crates/hoh-kernel` — контекст, fiber и его состояния, эффект с обратным действием, сервисы и области,
  реактивные зависимости, события пяти видов. Источник смысла: `vendor/cordis` и статья arXiv:2608.25512.
  Ядро проектируется заново, а не переводится построчно.
- `crates/hoh-kernel-macros` — объявление зависимостей плагина, проверяемое компилятором.
- `crates/hoh-loader` — строки конфигурации, группы, слои патчей (пакет → профиль → домашний каталог →
  командная строка), перекомпоновка без перезапуска. Источник: `vendor/loader`, `include`, `group`,
  `packages/boot/app-boot`, `cmdline`, `config-editor`.
- `crates/hoh-conformance` — прогон записанных сценариев dsh через наш собранный файл: вход пользователя
  и поток модели берутся из сценария, итоговый журнал и дерево файлов сравниваются с ожидаемыми.
  `conformance/EXPECTED.tsv` — статус каждого сценария; неприменимый сценарий получает письменную причину.
- `scripts/verify.sh` — единая итоговая проверка: сборка, тесты, сценарии; код возврата и отчёты.

Проверка этапа: перенесённые тесты ядра Cordis (17 файлов upstream и 14 файлов `scripts/cordis-*`,
`loader-*` из dsh) проходят; `hoh --dump-config` печатает собранное дерево профиля.

### Линия П. Продукт HoH (начинается после проверки этапа 1, идёт рядом с этапами 2–4)

- `crates/hoh-protocol` — типы и версии обмена между движком и приложением.
- `crates/hoh-server` — режим сервера: вход для каждого сотрудника, сопряжение устройства (строка-приглашение,
  одноразовый код, закреплённый отпечаток сертификата), WebSocket с JSON-RPC и передача файлов, очередь
  к модели с честным показом ожидания, учёт памяти, профиль «сервер + модель» с контрольным вызовом
  инструмента перед работой. Команда `hoh serve`.
- `crates/hoh-client` — связь, сопряжение, состояние и модели экранов без окна; проверяется против
  настоящего движка без отрисовки.
- `apps/hoh-desktop` — оболочка Tauri 2: сокет, поиск движка в сети, хранилище ключей, обновление.
- `ui/` (crate `hoh-ui`, Leptos в WebAssembly, вёрстка HTML и CSS) — единый чат, кнопка «Новая задача»,
  карточки задач, страница «Что я знаю об этой задаче», подтверждения, индикатор очереди, настройки.
  В окне слова «задача» и «помощник»; слова «плагин» нет. Русские строки.
- `crates/hoh-task` — задачи как плагины:
  - каталог задачи в стандарте Agent Skills (`SKILL.md`, `scripts/`, `references/`, `assets/`) плюс `hoh.toml`,
    `memory/`, `evals/examples/<n>/` (вход, одобренный результат, запись прогона), `.hoh/` (состояние, версии);
  - ход создания: описание → расспрос агентом → записанный прогон на примере → «да» или поправка →
    сохранение; состояния `draft`, `candidate`, `active`, `needs_recheck`, `quarantined`, `archived`;
  - приёмка каждой правки: проверка структуры, затем повтор всех одобренных примеров; не прошло — остаётся
    прежняя версия; откат без повторной генерации;
  - каркас каталога, заполнение через вызовы со строгой схемой и решение «принять или откатить» делает
    харнесс, а не модель; в первой версии задача декларативная, без скриптов, написанных моделью;
  - данные для страницы «Что я знаю»: правила компании, источники, шаблон результата, примеры; правка словами.
- `crates/hoh-tools-docs` — наши инструменты как плагины: чтение и запись xlsx и docx, текст из pdf, разбор
  HTML. Сканы читает сам Qwen. Ставятся тем же способом, каким позже будет ставиться marketplace.
- Упаковка для Linux (deb и AppImage) и обновление приложения с движка по локальной сети.

Проверка линии: сценарий «Новая задача» от описания до карточки и повторного запуска проходит без экрана
против настоящего движка с записанным потоком модели; вид экранов проверяется снимками в Chromium без
экрана; настоящее окно Tauri запускается под виртуальным дисплеем.

### Как идёт перенос

- Единица работы — один crate (один пакет dsh) или малая связка пакетов. В задании исполнителю: путь
  образца, каталог crate, `PORTING.md`, описание ядра, разрешённая проверка `cargo test -p <crate>`.
  Запрещено: трогать чужие crates, добавлять зависимости вне `DEPS.md`, что-либо устанавливать и запускать.
- Круг: писатель → его тесты проходят → ревьюер из другого семейства моделей сверяет Rust с исходником
  TypeScript (только чтение) → исправление → ведущий принимает и гоняет сценарии.
- Писатели: субагенты Sonnet, Codex, Kimi (после установки основателем). Ведущий: описание ядра, опись,
  сборка, сценарии, итоговая проверка. Лимит Claude бережём: объём идёт в Codex и Kimi.
- Прогресс виден по двум числам: сколько строк `MAP.tsv` в статусе `done` и сколько сценариев проходит.
  Скрипт `scripts/port-status.sh` печатает оба.
- Каждое намеренное отличие от образца записывается в `PORT_NOTES.md` внутри crate.

### Утвердить вместе с планом

1. Экспериментальные пакеты dsh заранее не переводим.
2. На время переноса сохраняем совместимость с dsh: формат журнала сессии V4, протокол SDK, имена строк
   конфигурации. Иначе их записанные сценарии нельзя использовать как приёмку.
3. Восемь пакетов проектируем заново, пять убираем, пять переносим после первой версии (список в `MAP.tsv`,
   решения `redesign`, `drop`, `after-v1`).
4. Сервер модели llama.cpp и `Qwen3.6-35B-A3B` ставим на `/mnt/toshiba` в конце этапа 1 для живой проверки
   адаптера, а не только перед бенчмарком.
5. Ставим стабильный тулчейн Rust и закрепляем версию (сейчас на машине ночная сборка 1.97 от мая).
6. Срок. Твой ориентир — около пяти дней на переписывание. Подтвердить его заранее я не могу: скорость
   упирается в лимиты трёх подписок. Порядок этапов такой, что после этапа 1 уже есть работающий агент.

## Definition of done

Первая версия для Linux готова, когда выполнено всё:

1. **Ядро.** Перенесённые тесты Cordis проходят.
2. **Перенос.** Каждая строка `MAP.tsv` этапов 0–4 в статусе `done`; у каждого crate проходят перенесённые тесты.
3. **Сценарии.** Каждый сценарий dsh из `snapshots/session`, `sdk`, `acp` либо проходит через собранный `hoh`,
   либо имеет письменную причину в `EXPECTED.tsv`. Пропусков без причины нет.
4. **Приложение.** Без экрана проходят: сопряжение с движком, чат со стримингом, «Новая задача» от описания
   до карточки, повторный запуск карточки на новом входе, правка правила словами на странице «Что я знаю»,
   подтверждение действия, показ очереди. Окно Tauri запускается под виртуальным дисплеем.
5. **Задача на живой модели.** На локальном Qwen задачи «документы → таблица» и «сайт → таблица» создаются
   через «Новая задача», одобряются на примере и выполняются на новом входе; после правки харнесс сам
   повторяет одобренные примеры.
6. **Бенчмарк.** Есть таблица «семья × условие» на локальной модели с долей верных результатов и числом
   вмешательств человека; тестовые экземпляры система при подстройке не видела.
7. **Итоговая проверка.** `bash scripts/verify.sh` завершается кодом 0, отчёты сохранены.
8. **Основатель.** Ты пробуешь руками и принимаешь решение. Пункты 1–7 — условие показа, а не замена твоей оценки.

Этап Windows готов, когда пункты 4 и 5 пройдены в виртуальной машине Windows 11 и установщик ставит приложение.
