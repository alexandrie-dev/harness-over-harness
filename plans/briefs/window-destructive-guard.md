# Подтверждение разрушающих действий внутри рабочей папки (профиль окна), 19.11 18:00

Решение CEO (условие вехи «опасные действия подтверждаются», принятый экран design/build-a/approval-1440.png:
«Выполнить команду в папке Документы/HoH: удалить 3 старых файла… Файлы не попадут в корзину»).
Сейчас в профиле окна (`apps/hoh/assets/bundle/window/cordis.patch.yml`, песочница workspace-write)
`rm` внутри папки сессии выполняется без вопроса; классификатора опасных команд нет ни в dsh, ни в порте.
Это сознательное отличие профиля окна от dsh. Профили, которые сверяются с dsh, не трогать.

## Шаг 1 — ворота, срок 30 минут (до разбора команд)
Проверить, что `PreToolDecision::Ask` (`crates/hoh-tools/src/pipeline.rs:297-345`, `service_ask`) в
host-режиме доходит до `approval/request` с mac (hoh-user-approval, мост в `apps/hoh/src/window_glue.rs`),
и решение хоста возвращается: rejected → инструмент не выполняется, allowed-once → выполняется.
Доказательство — тест в `apps/hoh/tests/` с пробным плагином, который на bash отвечает Ask, через
stdio собранного `hoh --profile window` (образец харнесса: `apps/hoh/tests/window_profile.rs`).
Если путь не работает и починка не укладывается ещё в 30 минут — ОСТАНОВИСЬ и сдай отчёт
`ПРИЧИНА шаг 1: …` (что не работает, где, оценка починки). Ведущий решает дальше.
Результат шага 1 сразу допиши в отчёт (раздел «Шаг 1»), не дожидаясь конца работы.

## Шаг 2 — плагин
Новый крейт `crates/hoh-window-destructive-guard` (без новых внешних зависимостей), подключён в профиль окна
и `apps/hoh/src/registry.rs`. Подписка на `ToolsPreExecute` (waterfall), только для инструмента bash
(инструменты файлов write/edit/apply_patch внутри папки — без вопроса, как сейчас).
Принцип: спрашиваем, когда нельзя исключить удаление или перезапись существующего файла. Обычные команды и
создание новых файлов — без вопроса.
Вопрос (Ask):
- rm, rmdir, unlink, shred, truncate; `find … -delete` / `-exec rm`; `xargs rm`;
- mv / cp, когда цель — существующий файл (или нельзя проверить); `>` (не `>>`) в существующий файл;
- git clean, git reset --hard, git checkout -- <файлы>/git restore; dd of=;
- непрозрачное: eval, `sh -c` / `bash -c` со строкой, конвейер в оболочку (`| sh`, `| bash`), source неизвестного.
Подстановку `$(…)` и обратные кавычки разбирать рекурсивно: безобидное внутри (`$(date)`) — без вопроса.
Разбор: свой токенизатор оболочки (кавычки, экранирование, `;`, `&&`, `||`, `|`, перенаправления,
подстановки); существование цели проверять относительно рабочей папки сессии. Неразбираемое → вопрос.
Текст вопроса человеческий (как на экране approval-1440): что будет сделано, с какими файлами (имена,
число), почему опасно («файлы не попадут в корзину»/«содержимое будет перезаписано»); сырая команда —
только в подробностях (поле reason/подробности), не в заголовке. Посмотри, какие поля approval/request
показывает окно (`ui/src`, `apps/hoh-desktop/src/approval.rs`), и заполни их соответственно.
PORT_NOTES крейта и `apps/hoh/PORT_NOTES.md`: отличие профиля окна от dsh и почему.

## Тесты (обязательны)
- unit в крейте: таблица команд → Ask/Allow, включая все пункты выше и обратные случаи;
- `apps/hoh/tests/window_profile.rs` (или отдельный файл): удаление файлов в рабочей папке →
  approval/request с mac → rejected → файлы на месте; allowed-once → удалены, и следующий такой же вызов
  снова спрашивает; обратная проверка — не меньше 10 обычных команд (ls, cat, grep, mkdir, запись нового
  файла через `>` в несуществующий, `$(date)`, конвейер без оболочки на конце, cp в новый файл, wc, echo)
  проходят без единого approval/request;
- `apps/hoh/tests/window_e2e.rs`: тот же сценарий удаления внутри папки (отклонить / разрешить).
