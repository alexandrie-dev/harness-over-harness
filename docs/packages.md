# Пакеты HoH: договор (HOH-27)

**Принято CEO 19.11.2026 00:52 как договор HOH-27.** Дата: 2026-11-19. Документ-договор; код хоста пакетов пишется после вехи «окно-чат». Решения взяты из `research/polyglot-packages.md` (**П**), `research/polyglot-node.md` (**Н**), `docs/window.md` (**О**) и CEO от 19.11. Добавленное от себя помечено «предложение». 
## 1. Что такое пакет

Пакет — папка, которой агент или человек добавляет сотруднику инструменты и подсказки. Четыре вида, один договор:

| Вид | `execution.kind` | Что внутри | Исполняется |
|---|---|---|---|
| Скилл | `skill` | `SKILL.md` (инструкция агенту) | ничем: только текст |
| Rust | `process` | готовая программа | отдельный процесс |
| Go | `process` | готовая программа | отдельный процесс |
| TypeScript | `node` | исходник `.ts` и готовый `.js` | наш Node, отдельный процесс |

Общее для всех: отдельный процесс, JSON-RPC по stdio, манифест с хешем и правами, отмена, права как пересечение (§4).

**Место в движке.** Хост пакетов — обычный Rust-плагин в статической композиции (`docs/kernel.md`): регистрирует инструменты через `ToolsService::register`, скиллы через `SkillRegistry::register_provider`. Выгрузка его fiber отменяет вызовы, снимает регистрации и завершает процессы (П п. 1). Чужие библиотеки в движок не загружаются.

**Что видит человек.** Слова «пакет» в окне нет: это «инструмент» (О §2). «Добавить инструмент» → «Проверяем зависимости» → права простыми словами («Читает: Документы/Отчёты; сайты: example.org») → отдельное окно «Разрешить и сохранить». В карточке сотрудника инструмент стоит в «Что умеет» вместе со своими правами.

## 2. Манифест

Файл `hoh-package.json` в корне пакета (имя — предложение, §8). Ключи в camelCase. Неизвестный ключ — отказ установки.

| Поле | Тип | Обязательно | Пример и смысл |
|---|---|---|---|
| `formatVersion` | целое | да | `1`. Версия формата манифеста |
| `id` | строка `[a-z0-9]+(-[a-z0-9]+)*` | да | `"notes"`. То же правило, что `is_skill_name` в `hoh-skill`. Ключ настроек и префикс инструментов |
| `version` | semver | да | `"1.0.0"` |
| `digest` | `"sha256:<64 hex>"` | да | см. ниже |
| `execution.kind` | `skill`\|`process`\|`node` | да | `"process"` |
| `execution.entry` | относительный путь | да | `"bin/read-note"`; для `skill` — `SKILL.md`; для `node` — `dist/index.js` |
| `execution.target` | `"<os>-<arch>"` | только `process` | `"linux-x86_64"`. Хост на другой цели пакет не включает |
| `execution.runtime` | `{"node": "<точная версия>"}` | только `node` | `{"node":"26.13.1"}`. Версия должна совпасть с поставляемым Node |
| `tools` | массив | нет | инструменты (ниже) |
| `skills` | массив `{name, path}` | нет | `[{"name":"notes-guide","path":"skills/notes-guide/SKILL.md"}]`; `name` по правилу `is_skill_name`, описание берётся из SKILL.md |
| `settingsSchema` | JSON Schema | нет | настройки пакета; значения хранятся под его `id` |
| `secrets` | массив `{name, description}` | нет | имена секретов настроек (ключ API); значения в манифесте и в `settings` не хранятся, см. §3 |
| `requestedPermissions` | объект | да (может быть пустым) | см. ниже |

**Инструмент** `{name, description, inputSchema, outputSchema}`, все четыре поля обязательны. `name` — по тому же правилу, что `id`; `description` — непустая. Схемы — ровно в подмножестве `hoh-tools/src/json_schema.rs`: один скалярный `type`, `properties`, `required`, булев `additionalProperties`, `items`, `enum`, `const`, `oneOf` (рядом с ним нельзя `properties`, `required`, `additionalProperties`, `items`, `enum`, `const`) и аннотации `description`, `title`, `default`, `examples`; схема из одних аннотаций допустима. Корень `inputSchema` — объект (`assert_object_json_schema`). Любое другое ключевое слово — отказ при установке. Сужений сверх валидатора нет. Выход проверяется по `outputSchema` на каждом вызове (в `ToolDefinition` это обязательный `output.schema`).

**Префикс имён (предложение).** Агент видит инструмент как `<id>__<name>`: `notes__read-note`. В `id` и `name` нет `_`, разбор однозначен. Занятое (в том числе встроенным) имя — пакет не включается; встроенные не замещаются (П п. 3).

**`digest` и снимок.** Два хеша одной формы (кодировка ниже, предложение).
- `digest` в манифесте — хеш файлов пакета, как их отдал автор; установка пересчитывает его, при расхождении отказ.
- `snapshotDigest` — хеш **неизменяемого установленного снимка**. Установка сначала собирает снимок: файлы пакета, а для `node` ещё `pnpm-lock.yaml`, дерево зависимостей из хранилища, собранный JS и ссылки, созданные установщиком. Человек одобряет именно этот снимок; исполнитель запускается только из него, на чтение; исходная папка после копирования не читается. Для `skill` и `process` хеши совпадают.

Кодировка списка, от которого берётся SHA-256: по строке на запись, по возрастанию байтов UTF-8 пути, строка заканчивается `\n`. Путь — относительный, в UTF-8 и в нормализации NFC, разделитель `/`, без начального `/`, пустых компонентов, `.`, `..`, `\` и NUL; повтор пути, в том числе после приведения к нижнему регистру, — отказ. Допустимы только записи `file` (`file\0<путь>\0<x|->\0<sha256 содержимого>`) и `link` (`link\0<путь>\0<относительная цель внутри снимка>`); `link` бывает только в снимке, созданном установщиком. Устройства, сокеты, жёсткие связи, пустые папки — отказ. **Метаданные:** `x` — единственный учитываемый бит, он ставится, если у файла в источнике есть любой бит исполнения; остальные права и время не входят в хеш, установщик выставляет в снимке `0555` для `x` и `0444` для `-`. Файл с setuid, setgid, sticky, xattr или capabilities — отказ. `execution.entry` вида `process` обязан иметь `x`. Манифест входит в список с удалённым `digest`, записанный как в `canonical_action` (ключи по порядку рекурсивно, компактно); хеш — `sha256:` и 64 символа hex в нижнем регистре. Node и pnpm в хеш не входят: их закрепляют `runtime` и хеш поставки (Н §1). Хост пересчитывает `snapshotDigest` перед каждым запуском процесса; расхождение — отказ.

**`requestedPermissions`** (имена — предложение; значения согласованы с `Permissions` в `hoh-protocol`):

```json
{ "files":   { "read": ["$granted"], "write": [] },
  "network": { "domains": [] },
  "programs": [] }
```

`"$granted"` значит «любые папки, выданные сотруднику». `network.domains` — для `host/http.request`; `programs` — имена для `host/process.run`. У `skill` все три списка пустые.

## 3. Протокол пакет ↔ движок

JSON-RPC 2.0, одно сообщение на строку UTF-8 (`\n`), без переносов внутри. Протокол отдельный от окно↔движок (П п. 3). **stdout — только сообщения**: другая строка — нарушение, процесс убивается. **stderr — журнал** с `id` пакета.

**Движок → пакет.**

- `initialize` {`protocolVersions:[1]`, `host:{name,version}`, `package:{id,version,snapshotDigest}`, `settings`, `limits:{maxFrameBytes,callTimeoutMs,memoryBytes}`} → {`protocolVersion:1`, `capabilities:{cancel:true}`, `tools:[имена]`}. Ответ — за 10 с и не больше 64 КиБ, иначе процесс убит. Список `tools` обязан совпасть с манифестом, иначе пакет отключается. Повторный `initialize` — ошибка.
- `tools/call` {`tool` (локальное имя), `arguments`, `context:{packageId,snapshotDigest,sessionId,callId,grantRef}`} → {`output`}. Идентичность назначает движок. Обратный запрос ищет `callId` только в таблице вызовов **своего транспорта и своего поколения процесса**; пакет, сессия и права берутся из найденной записи. Чужой или устаревший `callId` — ошибка `-32600`, и сведений о других вызовах пакет не получает.
- `cancel` (уведомление) {`callId`}. Пакет прекращает работу и отвечает на вызов ошибкой `-32002`; порядок — ниже.
- `shutdown` → `{}`. После ответа хост закрывает stdin и ждёт 5 с.

**Жизненный цикл (v1).** Вызовы одного процесса идут строго по одному: хост не шлёт второй `tools/call`, пока первый не завершён. Если процесс вышел, незавершённый вызов падает, **автоматического повтора нет** (запись могла частично пройти). Следующий вызов запускает новый процесс — новое поколение: хост заново шлёт `initialize`, все прежние `callId` недействительны.

**Отмена, выключение, удаление.** При `cancel`, `shutdown`, отключении и `remove` хост в таком порядке: (1) сразу закрывает приём обратных запросов этого вызова (процесса); (2) отменяет его незавершённые операции брокера: HTTP, запись, `process.run`; (3) убивает и дожидается всех потомков процесса; (4) только потом освобождает запись вызова. Поздние ответы отбрасываются. **Отмена против завершения** решается одним порядком обработки на стороне хоста: если `output` принят раньше отмены, вызов успешен, `cancel` игнорируется; если раньше принята отмена, `output` отбрасывается и вызов завершается `-32002`.
**Пакет → движок** (только внутри активного вызова, в параметрах всегда `callId`).

| Метод | Параметры | Ответ |
|---|---|---|
| `host/fs.read` | `{callId,folder?,path,offset?,length?,encoding:"utf8"\|"base64"}` | `{data,encoding,size,eof,nextOffset?}` |
| `host/fs.write` | `{callId,folder?,path,data,encoding,mode:"create"\|"overwrite"\|"append"}` | `{size}` |
| `host/fs.list` | `{callId,folder?,path,cursor?,limit?}` | `{entries:[{name,kind,size}],nextCursor?}` |
| `host/fs.stat` | `{callId,folder?,path}` | `{kind,size,mtime}` |
| `host/http.request` | `{callId,method,url,headers?,body?(base64),timeoutMs?,maxBytes?}` | `{status,headers,body(base64),truncated}` |
| `host/process.run` | `{callId,program,args,cwd?,stdin?,timeoutMs?}` | `{exitCode,stdout,stderr,truncated}` |
| `host/secret.get` | `{callId,name}` | `{value}` |

Движок проверяет права каждого запроса заново (§4). Прямых сокетов и запуска программ минуя движок у пакета нет.

**Файлы.** Все операции брокера — `fs.read/write/list/stat`, включая место создания при записи — идут **относительно одной выданной папки** (`folder` называет её; если она одна, поле можно опустить). Абсолютные пути и `..` отвергаются. Хост не проверяет путь заранее, а открывает его покомпонентно от дескриптора выданной папки, не следуя ссылкам (на Linux `openat2` с `RESOLVE_BENEATH` и `RESOLVE_NO_SYMLINKS`, ядро 5.6+; предложение; нет возможности — запуск запрещён, §4). Поэтому ссылка наружу и подмена пути между проверкой и открытием не срабатывают. Запись так же открывает родителя и создаёт файл с `O_EXCL` либо заменяет атомарно внутри него. Запрет ссылок в дереве пакета выданные папки не защищает, эта проверка обязательна.

**HTTP.** DNS, каждое перенаправление и локальные адреса проверяются на каждом шаге; домены — `network.domains` пакета ∩ права сотрудника и задачи.

**Программы.** `host/process.run` идёт в той же песочнице (база ниже), **без сети**: в v1 у дочерних программ пакета её нет совсем. Сеть пакет получает только через `host/http.request` по своим `network.domains`. `program_network` сотрудника на пакеты не распространяется: согласие пакета не может выразить такое право (предложение).

**Секреты.** Решено: секреты настроек (ключ API) входят в первую реализацию хоста. Пакет объявляет имена в `secrets`. Значения лежат в `hoh-credentials` под ключом (предложение: область `package-<id>`, имя секрета) и задаются человеком write-only методом `hoh/package/secret/set {id,name,value}` (не привилегированный: прав не расширяет; назад значение окну не отдаётся). В `initialize` и `settings` пакет получает только имена. Значение пакет запрашивает `host/secret.get` внутри вызова, только по объявленному имени; вне вызова и для чужого `id` — ошибка `-32040`. Хост держит значение в обёртке без `Debug` и `Serialize`: оно не попадает в журнал, события сессии и вывод `Debug`; в окружение и аргументы процесса его кладёт только сам пакет. Ответ пакета с чужим значением хост не фильтрует.

**База изоляции.** Единая и обязательная для любого исполнителя (`process`, `node`) и каждого его потомка, включая `process.run`. Чистое окружение: переменные задаёт хост, без `LD_*`, `NODE_*` и секретов; закрыты все дескрипторы, кроме stdin, stdout и stderr; лимиты на число файлов, процессов, память, время и вывод; нет доступа к памяти и `/proc` хоста и чужих процессов (отдельные PID и монтирование, запрет `ptrace`); код и зависимости только для чтения; **выданные папки внутрь песочницы не монтируются**: любой исполнитель (в том числе нативный) и дети видят только снимок и пустую временную папку вызова, а файлы пользователя — лишь через `host/fs.*`, где работает пересечение прав пакета, сотрудника, задачи и вызова; сеть закрыта. Поэтому `cwd` у `process.run` лежит во временной папке. На Linux — bubblewrap/Landlock (Н §3).

**Коды ошибок (предложение).** Стандартные `-32700…-32603`, плюс: `-32001` ошибка инструмента или выход процесса; `-32002` отменено; `-32003` лимит; `-32010` путь запрещён; `-32011` не найдено; `-32020` домен не выдан; `-32021` сетевая ошибка; `-32030` программа не разрешена; `-32040` секрет не объявлен или не задан. Текст ошибки пакета агент получает как данные.

**Лимиты (предложение, подбираются измерением; настраивает хост).** Кадр 1 МиБ считается по **сериализованной** строке, после экранирования JSON и base64. Поэтому хост сам ограничивает ответы: `fs.read` отдаёт не больше 128 КиБ сырых байт за запрос (`length` больше — усекается, продолжение по `nextOffset`); `fs.list` — страницами до 500 записей (`cursor`); `http.request` и `process.run` — не больше `maxBytes` (умолчание и максимум 256 КиБ) с `truncated:true`. Не поместившийся ответ хост усекает, а не шлёт большой кадр. `output` — не больше 1 МиБ сериализованным, иначе `-32003`. Кадр больше лимита — процесс убит. Вызов 60 с или `timeout_ms` инструмента; **тишина**: если за `callTimeoutMs` нет ни одного кадра, вызов завершается `-32003`; память процесса 256 МиБ; `stderr` 64 КиБ на вызов. Превышение — процесс убит, вызов завершён `-32003`. **Вывод между вызовами:** любой байт в stdout вне ответа на запрос — нарушение, процесс убит; в stderr между вызовами (от завершения одного до начала следующего, а также в простое) бюджет 16 КиБ. Хост читает и отбрасывает лишнее; превышение — процесс и потомки остановлены, следующий вызов запускает новое поколение.

## 4. Права

**Пересечение.** Действующие права вызова — пересечение четырёх наборов: (1) что пакет запросил и человек одобрил; (2) права сотрудника (`Permissions`: интернет, домены, папки, запись, программы; `program_network` на пакеты не распространяется); (3) права задачи, если вызов идёт из неё; (4) сам вызов — например, путь в аргументах. Недоступное хотя бы в одном — отказ. Пакет не расширяет права сотрудника: `programs: false` у сотрудника запрещает `host/process.run`, что бы ни написано в манифесте.

**Когда спрашивается человек.** Только при выдаче или расширении прав: включение, новая версия, откат. Новый сайт во время вызова обрабатывается обычным путём сотрудника (режим «спрашивать», О §3). Запуск процесса исполнителя пакету права на программы не даёт (П п. 4).

**Связь с подтверждением.** Действие для `approval/request` по `hoh-protocol` — объект ровно с `method` и `params`. Для пакета это `{method:"hoh/package/enable", params:{id, version, snapshotDigest, enabled:true, grantedPermissions, settingsHash}}`. Поля и нормализация: одна функция в `hoh-protocol` строит действие из запроса `hoh/package/enable {id, version, enabled, grant?, settings?}`; ядро окна и движок считают ею `actionHash`:
- `id`, `version` — как в запросе; `snapshotDigest` — хеш хранимого снимка этой версии (не из запроса);
- `enabled` — всегда `true` (подтверждается только включение);
- `grantedPermissions` — это `grant` запроса в нормальном виде (нет `grant` — ровно `requestedPermissions`): списки без повторов и по возрастанию байтов, домены в нижнем регистре и punycode, папки абсолютными без `..` (`"$granted"` раскрыт в конкретные папки сотрудника), всё сверх `requestedPermissions` — отказ;
- `settingsHash` — `sha256:` + hex от `canonical_action` записи настроек после проверки по `settingsSchema` (нет `settings` — прежние настройки этого `id`, для первого включения `{}`).

Одобряется ровно тот снимок, из которого потом запускается процесс. `actionHash` = SHA-256 канонической записи; MAC = HMAC-SHA256 ключом хоста от `{approvalId, outcome, actionHash, risk, humanText, expiresAt}`. Подмена после показа при том же MAC невозможна. Риск (предложение): программы — `high`; запись файлов или сеть — `medium`; только чтение — `low`.

**Обновление.** Новый `snapshotDigest` — это всегда новое подтверждение, даже если права те же: MAC привязан к байтам. До решения работает прежняя одобренная версия (Н §3), новая лежит рядом со статусом `needs_review`. Откат — повторное включение старой версии, тоже с подтверждением.

**Версия задачи закрепляет пакет.** Версия задачи, которая вызывает инструмент пакета, хранит ссылку `{id, version, snapshotDigest}` (П п. 5). Включение новой версии пакета не меняет сохранённые версии задач: они идут на закреплённом снимке. Если он удалён или не одобрен, задача не запускается («инструмент недоступен»), а не переключается молча. Новая версия пакета подхватывается новой версией задачи с новой ссылкой (обычное «да» в `hoh/task/draft/decide`).

**Недоступная песочница.** Если нет любого пункта базы изоляции (§3), запуск **запрещён**: статус `blocked`, причина простым текстом. Исключение — `skill`: у него нет процесса и нет прав.

## 5. Node для TypeScript

Только то, что принято в `research/polyglot-node.md`; новых решений нет.

- **Откуда Node.** Официальный бинарник, закреплённая LTS (на 19.11 — 26.13.1), отдельно по ОС/архитектуре. Проверка: подпись `SHASUMS256.txt.asc` закреплёнными отпечатками ключей, затем SHA-256 архива. Node лежит в нашей подписанной поставке, запуск по абсолютному пути; Node пользователя не используем.
- **Зависимости.** Пользователь и агент идут одним путём: установщик берёт исходники и список зависимостей, чужие `.npmrc`, `.pnpmfile.*`, `node_modules` отбрасывает. Закреплённый pnpm 12.21.0. `minimumReleaseAge: 10080` (7 суток) и `Strict: true`, `IgnoreMissingTime: false`, `trustLockfile: false`, исключений нет. `ignoreScripts`, `allowBuilds: {}`, `strictDepBuilds`, `ignorePnpmfile`: скриптов нет. Запрещены git/URL-зависимости, `binding.gyp`, нативные модули. Всё дерево с SHA-512; проверяем даты, хеши, лицензии, известные уязвимости.
- **Без сети при установке.** Получение идёт через наш посредник со списком «имя—версия—хеш» и единственным источником registry.npmjs.org; затем `pnpm fetch`, потом `install --offline --frozen-lockfile --ignore-scripts`. Недостающий архив — ошибка. Новые имена показываются явно.
- **TypeScript.** Пакет поставляет готовый JS; преобразование TS делает отдельный ограниченный шаг нашим закреплённым компилятором. Встроенная в Node стирка типов для этого не годится: она не проверяет типы и игнорирует `tsconfig`.
- **Песочница.** Каждый инструмент — отдельный процесс под единой базой изоляции (§3: bubblewrap/Landlock, чистое окружение без `NODE_OPTIONS`, `NODE_PATH`, `LD_PRELOAD`, секретов, код только для чтения, лимиты). Сверху флаги `--permission`/`--allow-fs-read` (только код; в отличие от Н §3, выбранные файлы пользователя Node напрямую не читает, §3) как дополнительный предохранитель: без дочерних процессов, нативных модулей, FFI, inspector, прямой сети. Сеть закрыта ОС; HTTP идёт через `host/http.request`. Профиль Node пока не написан.
- **В окне** (кроме шагов из §1): причины отказа простым текстом («Версия слишком новая, доступна с 25 ноября», «Контрольная сумма не совпала», «Нужен неподдерживаемый нативный модуль») и предупреждение: разрешённые данные всё ещё могут уйти на разрешённый сайт, неделя и хеш не доказывают добросовестность кода.

В П вид `javascript`, здесь `node` (CEO).

## 6. Методы окна

Новые методы с префиксом `hoh/` (таблица в `hoh-protocol`):

| Метод | Параметры → результат | Привилегированный |
|---|---|---|
| `hoh/package/list` | `{}` → `{packages:[PackageInfo]}` | нет |
| `hoh/package/get` | `{id}` → `PackageInfo` + `manifest` + `permissionDiff?` | нет |
| `hoh/package/install` | `{path}` → `PackageInfo` со статусом `installed` или `needs_review` | нет |
| `hoh/package/enable` | `{id, version, enabled, grant?, settings?}` → `PackageInfo` | да, если `enabled: true` |
| `hoh/package/remove` | `{id, version?}` → `{}` | нет |
| `hoh/package/secret/set` | `{id, name, value}` → `{}` (write-only) | нет |

`PackageInfo` (П п. 5): `{id, version, digest, snapshotDigest, kind, status, tools, requestedPermissions, grantedPermissions, error?}`; `status` — `installed`, `enabled`, `disabled`, `needs_review`, `blocked`, `failed`. Уведомление `package.changed` `{id, version, change: created|updated|deleted}` (как `task.changed`).

**Почему так привилегируем (разбиение `install`/`enable` — предложение автора документа, не решение исследования).** `install` инертен: собирает неактивный снимок, ничего из пакета не запускает, прав не выдаёт (для `node` работает наш установщик, не код пакета), поэтому подтверждения не нужно. Начни `install` исполнять код пакета, он стал бы привилегированным. Права выдаёт `enable`: включение, откат старой версии, обновление (новая версия ставится `install`, включается `enable`) и сохранение настроек. Поэтому `hoh/package/enable` добавляется в `PRIVILEGED_METHODS`, а в `requires_host_approval` — условие `enabled == true`. Выключение и `remove` права только уменьшают. Это согласуется с П п. 5.

## 7. Пример: `read-note({path}) → {text}`

Инструмент читает заметку из выданной папки. `inputSchema`: `{"type":"object","properties":{"path":{"type":"string"}},"required":["path"],"additionalProperties":false}`; `outputSchema`: то же с `text`. Права: чтение `["$granted"]`, остальное пустое.

**Rust** (Go отличается только `go.mod`, `main.go` вместо `Cargo.*`, `src/`):
```
read-note-rs/
  hoh-package.json    kind process, entry bin/read-note, target linux-x86_64
  bin/read-note       готовая программа
  src/main.rs, Cargo.toml, Cargo.lock    (не обязательны)
```

**TypeScript.**
```
read-note-ts/
  hoh-package.json    kind node, entry dist/index.js, runtime {"node":"26.13.1"}
  src/index.ts        исходник
  dist/index.js       готовый JS (собран закреплённым компилятором)
  package.json        прямые зависимости, точные версии (необязательно)
  pnpm-lock.yaml      нужен, если есть зависимости
```
**Скилл.**
```
read-note-skill/
  hoh-package.json    kind skill, entry SKILL.md, tools [], requestedPermissions пусто
  SKILL.md            name: read-note; description: Читать заметку; текст: как прочесть файл штатным инструментом
```
Скилл не исполняет функцию: он учит агента читать файл штатным инструментом, результат зависит от модели (П, «Автор»). Единого внешнего инструмента для четырёх видов пока нет (§8).

**Диалог программы (Rust/Go/TS одинаков):**
```
→ {"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersions":[1],…}}
← {"jsonrpc":"2.0","id":1,"result":{"protocolVersion":1,"capabilities":{"cancel":true},"tools":["read-note"]}}
→ {"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"tool":"read-note","arguments":{"path":"notes/a.md"},"context":{"callId":"c7",…}}}
← {"jsonrpc":"2.0","id":100,"method":"host/fs.read","params":{"callId":"c7","path":"notes/a.md","encoding":"utf8"}}
→ {"jsonrpc":"2.0","id":100,"result":{"data":"Привет","encoding":"utf8","size":12,"eof":true}}
← {"jsonrpc":"2.0","id":2,"result":{"output":{"text":"Привет"}}}
```
Приёмка каждого вида (П): установка, видимость, вызов, отказ вне папки (`-32010`) и в сети, отзыв прав, падение, выгрузка.

## 8. Откладывается, решено, решает реализация

**Откладывается.** Вызовы пакетов друг другом (в v1 их нет: у пакета нет метода вызова инструмента); несколько ОС и целей в одном пакете; код хоста (после «окна-чата»); WASM (П: 2–4 недели на пробу); QuickJS вместо Node; macOS и Windows; Node пользователя; нативные npm-модули; параллельные вызовы одного процесса; экспорт сервисов, UI-кода и подписок на события; каталог и подпись издателя (есть только хеш, не доверие к автору).

**Решено.**

- **Агент пишет и ставит пакеты сам** (пожелание основателя «агент может добавлять какие-то тулзы»). Он делает это служебным инструментом хоста (имя решает реализация) через тот же конвейер, что `hoh/package/install`: снимок, проверки, для `node` наш установщик. Пакет остаётся неактивным. Включение, то есть `enable`, всегда подтверждает человек в отдельном окне; агент подтвердить не может. Пакеты друг друга в v1 не вызывают.
- **Секреты настроек** — через `hoh-credentials`, в первой реализации хоста (§3, «Секреты»).
- **Одна цель на пакет, сейчас Linux;** несколько ОС и массив `execution` — позже.
- Профиль песочницы не написан; до него включаются только скиллы.

**Решает реализация.** Имя файла `hoh-package.json` рядом с крейтом `hoh-package-manifest`; общий внешний инструмент для четырёх видов (П: task-tool); числа лимитов §3 (предложения без измерений); параллельные вызовы одного процесса (v1 — по одному; позже нужен признак в манифесте и отмена по `callId`); окончательная таблица кодов ошибок и число подряд разрешённых перезапусков упавшего процесса (повтора вызова нет).
