# Плагины HoH: единый договор HOH-27 / HOH-42

Статус: предлагаемая спецификация будущей реализации; невыбранные решения
перечислены в § 12. Дата: 2026-11-23.
Этот документ сводит договор пакетов HOH-27 с политикой плагинов HOH-42. В
пользовательском интерфейсе и документации используется слово **«плагин»**.
Слово «пакет» ниже означает только папку или неизменяемый снимок файлов плагина.

Пометки в документе:

- **сегодня** — подтверждено исходным кодом текущего дерева;
- **будет** — нормативное требование к хосту плагинов, которого в коде ещё нет;
- **не проверено** — свойство платформы или число, которое надо подтвердить до реализации.

## 1. Цель и неизменяемые правила

Плагин должен быть простым в написании, иметь один манифест и уметь заменять
любую встроенную прикладную часть HoH. Один и тот же снимок можно сначала включить
как пользовательский, а затем положить во встроенную поставку без переписывания.

Есть два уровня встроенности. **Bundled plugin** — неизменённый `skill`, `process`
или `node`, вложенный в подписанную поставку; он остаётся в тех же брокерах,
песочнице и UI-изоляции. **Trusted core** — отдельно проверенный `rust-inproc` или
интерфейс самого ядра, скомпилированный с продуктом и получивший внутренние права
только решением подписанной сборки.

Поддерживаются четыре авторских формата:

| Формат | Исполнение | Для чего |
|---|---|---|
| MD | `skill` | `SKILL.md`: инструкция модели, без исполнения кода |
| Rust | `process` или `rust-inproc` | изолированный готовый бинарник либо часть подписанной сборки |
| Go | `process` | изолированный готовый бинарник |
| TypeScript | `node`, при необходимости `ui.entry` | готовый JS в закреплённом Node и модуль интерфейса окна |

Правила, которые не зависят от формата:

1. Источник истины — `hoh-package.json` и точный `snapshotDigest`. Описания,
   схемы, права и вклады живут в манифесте; исполняемый код связывает только их
   `id` с обработчиками и не переопределяет договор.
2. Объявление вклада не выдаёт право на него. Ядро отдельно проверяет манифест,
   одобрение человека и права каждого вызова.
3. Плагин не получает сырой доступ к сервисам ядра. Внешний процесс видит только
   версионированный протокол и брокеры.
4. Регистрация сверх `contributes`, запрос необъявленного сервиса или права и
   ответ вне схемы отклоняются.
5. Обычный плагин может только сузить защитное решение или попросить человека.
   Он не может превратить уже запрещённое действие в разрешённое.
6. Неизменяемый фундамент контроля остаётся в Rust-ядре (§ 8).

## 2. `hoh-package.json`

### 2.1. Общая форма

**Будет:** формат манифеста HOH-42 имеет `formatVersion: 2`. Неизвестное поле,
неизвестный вариант закрытого перечисления и несовпадение схемы означают отказ
до исполнения какого-либо кода плагина.

Версия 2 заменяет проектный `formatVersion: 1` из HOH-27 именно для нового хоста
плагинов. Манифест v1 не принимается как v2 и не получает UI, хуки или замены
неявно; для него потребуется явная миграция.

Пример формы (не шаблон со всеми возможными полями):

```json
{
  "formatVersion": 2,
  "id": "notes",
  "version": "1.0.0",
  "digest": "sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "execution": {
    "kind": "node",
    "entry": "dist/index.js",
    "runtime": { "node": "26.13.1" }
  },
  "ui": { "entry": "dist/ui.js" },
  "settingsSchema": { "type": "object", "additionalProperties": false },
  "secrets": [{ "name": "api-key", "description": "Ключ Notes API" }],
  "requestedPermissions": {
    "files": { "read": ["$granted"], "write": [] },
    "network": { "domains": ["api.example.org"] },
    "programs": [],
    "conversation": { "read": false },
    "hooks": ["tools/pre-execute"],
    "prompt": ["section"],
    "executor": { "register": false, "replace": false },
    "ui": ["panelItem", "page"],
    "replace": ["tools:core.read"]
  },
  "contributes": {
    "tools": [],
    "skills": [],
    "promptSections": [],
    "hooks": [],
    "approvals": [],
    "executors": [],
    "ui": { "panelItems": [], "pages": [], "paletteCommands": [], "buttons": [] }
  },
  "requires": {
    "services": {
      "tools": { "protocolVersions": [2] },
      "ui": { "protocolVersions": [1] }
    }
  }
}
```

### 2.2. Поля верхнего уровня

| Поле | Требование |
|---|---|
| `formatVersion` | Обязательно; целое `2` для этого договора |
| `id` | Обязательно; `[a-z0-9]+(-[a-z0-9]+)*`; постоянный владелец вкладов, настроек, секретов и RPC-пространства |
| `version` | Обязательно; SemVer |
| `digest` | Обязательно; `sha256:` и 64 строчных hex; хеш готового авторского набора, который вычисляет `hoh plugin pack`, а не правит автор вручную |
| `execution` | Обязательно; ровно один вариант из § 3 |
| `ui` | Необязательно; только `entry` собранного JS-модуля интерфейса (§ 4) |
| `settingsSchema` | Необязательно; JSON Schema настроек; значения хранятся под `id` |
| `secrets` | Необязательно; массив уникальных `{name, description}`; значений в манифесте и настройках нет |
| `requestedPermissions` | Обязательно, может быть пустым; верхняя граница того, что человек вообще может выдать |
| `contributes` | Обязательно, может быть пустым; полный статический список вкладов |
| `requires.services` | Обязательно, может быть пустым; сервисы ядра и допустимые версии их протоколов |

**Будет:** `hoh plugin pack` до установки создаёт готовые результаты сборки и
вычисляет `digest`. Установка не запускает код, менеджер пакетов или компилятор:
она проверяет готовый набор файлов, строит неизменяемый снимок и вычисляет
`snapshotDigest`. Человек одобряет, задача закрепляет, а исполнитель запускает
именно тройку `{id, version, snapshotDigest}`. Если преобразований нет, `digest`
и `snapshotDigest` совпадают. Пара `{id, version}` навсегда связана с одним
авторским `digest`; другие байты требуют новой версии и отклоняются до включения.

Канонизация хеша сохраняется из HOH-27: относительные NFC-пути UTF-8, `/` как
разделитель, без пустых частей, `.`, `..`, `\` и NUL; сортировка по байтам пути;
обычные файлы и только созданные установщиком внутренние ссылки; отказ для
устройств, сокетов, hardlink, setuid/setgid, xattr и capabilities. Учитываются
содержимое и единственный бит «исполняемый». Манифест входит в хеш без поля
`digest`. Перед каждым запуском хост пересчитывает `snapshotDigest`.

### 2.3. `execution`

`execution` — закрытое объединение по `kind`:

- `skill`: `{kind, entry}`; `entry` указывает на `SKILL.md`. Код не запускается,
  все исполняемые права пусты, допустимы только вклады `skills`; в первой версии
  у `skill` нет `ui.entry`;
- `process`: `{kind, entry, target}`; `entry` — готовый исполняемый файл Rust или
  Go, `target` — одна точная пара ОС/архитектуры, сначала `linux-x86_64`;
- `rust-inproc`: `{kind, key}`; `key` — устойчивый ключ реализации, скомпилированной
  с продуктом. Это не путь к динамической библиотеке;
- `node`: `{kind, entry, runtime}`; `entry` — готовый JS, а `runtime.node` — точная
  версия Node из подписанной поставки. Node пользователя не используется.

`process`, `node` и `rust-inproc` могут иметь отдельный `ui.entry`.
Интерфейсная часть всегда является собранным TypeScript/JavaScript и проходит
отдельную границу § 4.

### 2.4. `contributes`

Каждый вклад имеет уникальный внутри плагина `id`, человекочитаемое название и,
если принимает или возвращает данные, закрытую JSON-схему. Полное имя строится
ядром из `plugin id` и `contribution id`; совпадение имени не заменяет чужой
вклад молча.

Поддерживаемые вклады:

- `tools`: имя, описание, `inputSchema`, `outputSchema`, необязательный предел
  времени и необязательное явное `replaces`;
- `skills`: имя и относительный путь к `SKILL.md`;
- `promptSections`: имя, место/порядок, статический текст или имя провайдера,
  необязательное явное `replaces`;
- `hooks`: подписка на `agent/pre-step`, `agent/request`, `tools/pre-execute`,
  `tools/execute`, `tools/post-execute` или `tools/result`, плюс схема допустимого
  ограниченного ответа;
- `approvals`: защитный вклад для конкретного действия или класса действий.
  Его единственные содержательные ответы — `deny` и `request`; отсутствие ответа
  означает «нет мнения». Ответа `allow` в протоколе нет;
- `executors`: исполнитель с именем, возможностями и явным `replaces` при замене;
- `ui.panelItems`, `ui.pages`, `ui.paletteCommands`, `ui.buttons`: пункт панели,
  страница, команда палитры и кнопка. Каждый указывает локальный обработчик и
  только принадлежащие плагину RPC-схемы.

`replaces` — явная ссылка на слот или вклад. **Будет:** замена показывается
человеку при включении, требует отдельного права и никогда не возникает только
из-за совпадения имени. После выгрузки плагина прежний вклад восстанавливается.
Так внешний плагин сможет заменить встроенный инструмент, раздел промпта, шаг,
исполнителя или элемент окна без правки своего кода.

Заменять можно только слот, который ядро явно объявило заменяемым. У слота один
активный владелец: если два включаемых плагина требуют один слот, включение
блокируется до выбора человека, а порядок загрузки ничего не решает. Системное
подтверждение, рамка внешнего UI и другие защитные места окна не заменяются.
Восстановление прежнего владельца после выгрузки — требование будущей реализации,
а не свойство нынешнего `set_executor`.

### 2.5. `requires.services`

Ключ — стабильное имя сервиса (`tools`, `skills`, `prompt`, `hooks`, `executor`,
`ui`, `pluginRpc` и другие объявленные ядром). Значение содержит непустой список
точных целых `protocolVersions`. До включения ядро выбирает общую версию для
каждого сервиса. Нет общей версии, сервис не объявлен или плагин обращается к
сервису вне списка — плагин не запускается.

Это договор протокола, а не доступ к Rust `Service<T>`: сырой сервис получают
только `rust-inproc`-реализации, которым его выдала подписанная сборка.

## 3. Исполнение процесса и протокол v2

### 3.1. Транспорт и инициализация

**Будет:** `process` и `node` общаются с ядром по JSON-RPC 2.0 через stdio.
Одна строка UTF-8 — один кадр; stdout содержит только протокол, stderr — журнал с
меткой плагина. Любая посторонняя строка stdout или кадр сверх лимита останавливает
процесс и его потомков.

Первый запрос ядра:

```text
initialize {
  protocolVersions: [2],
  host: {name, version},
  plugin: {id, version, snapshotDigest},
  services: {<name>: <selected version>},
  settings,
  secrets: [<declared names>],
  limits
}
```

Ответ выбирает версию `2`, объявляет поддерживаемые возможности и открывает фазу
регистрации. Плагин регистрирует только то, что уже есть в `contributes`, через
типизированные мосты:

- `tools.register`, затем вызовы `tools/call`;
- `skills.register`;
- `prompt.section`, `prompt.context`, `prompt.assemble`;
- `hooks.subscribe`, события и `hooks.respond`;
- `executor.register`, затем вызовы исполнителя по договору внешнего харнесса;
- `ui.contributions` и события состояния окна;
- `pluginRpc.register` для методов из пространства § 5.

Ядро завершает регистрацию атомарно: либо все объявления совпали с манифестом,
схемами, правами и доступными сервисами, либо поколение процесса не публикует ни
одного вклада. Произвольный callback `next()` наружу не передаётся. Ядро само
ведёт цепочку и принимает только перечисленное решение или ограниченный patch.

Описания, JSON-схемы и права не повторяются в runtime-регистрации: их единственный
источник — манифест. Процесс передаёт только `contributionId` и `handlerId`, а
ядро связывает их с уже проверенной записью. Неизвестный или лишний обработчик,
несовпадение множества обработчиков и попытка подменить схему означают отказ всей
атомарной регистрации.

### 3.2. Обратные брокеры

Процесс может обращаться к ядру только в рамках активного вызова или события:

- `host/fs.read`, `host/fs.write`, `host/fs.list`, `host/fs.stat`;
- `host/http.request`;
- `host/process.run`;
- `host/secret.get`.

Во всех запросах есть назначенный ядром `callId`/`eventId`. Запись ищется только
в таблице этого транспорта и этого поколения; личность плагина, сессия,
`snapshotDigest` и набор прав берутся из таблицы, а не из параметров плагина.
Чужой, завершённый или прежний идентификатор отклоняется без раскрытия данных.

Секрет доступен только по имени из `secrets`, только своему `id`, только внутри
разрешённой операции. Значение не попадает в `initialize`, окружение, журнал,
события или чтение из окна. Интерфейс задаёт секрет write-only.

### 3.3. Отмена, поколения и завершение

На `cancel {callId|eventId}` процесс прекращает работу и отвечает ошибкой
«отменено». При отмене, выключении, обновлении и удалении ядро по порядку:

1. закрывает новые обратные запросы поколения;
2. отменяет его HTTP, файловые записи и запущенные программы;
3. останавливает и дожидается всех потомков;
4. снимает вклады и только затем освобождает записи вызовов.

Принятый до отмены ответ остаётся ответом; принятая раньше отмена делает поздний
ответ недействительным. Автоматического повтора вызова после падения нет: запись
могла частично выполниться. Следующий вызов создаёт новое поколение, повторяет
`initialize` и регистрацию; идентификаторы старого поколения недействительны.

### 3.4. Таймауты хуков и политика отказа

Предел каждого хука задаёт ядро и сообщает в `initialize`; плагин не может его
увеличить. Таймауты хуков короче общего инструментального вызова и различаются по
точке. **Точные числа будут выбраны измерением; сейчас не проверено.**

Отказ всегда однозначен:

- защитный хук/`approvals` при таймауте, падении, отмене или неверном ответе
  закрывает действие (`deny`); разрешение по умолчанию невозможно;
- хук, способный изменить шаг, промпт, аргументы или результат, при ошибке
  завершает текущую операцию ошибкой и отключает это поколение плагина; цепочка
  не продолжается с частичным patch;
- наблюдающее событие интерфейса не задерживает ядро: потерянное событие
  отмечается, а неисправный UI-вклад отключается.

Для защитных вкладов допустимы только `deny` и `request`. `request` передаёт
решение штатному брокеру подтверждений; только подписанный ответ человека может
снять запрос. Плагин не получает MAC и не отвечает от имени человека.

### 3.5. Лимиты

Сохраняются начальные пределы HOH-27: `initialize` — до 10 секунд и 64 КиБ;
сериализованный кадр и итоговый `output` — до 1 МиБ; обычный вызов — до 60 секунд;
память процесса — 256 МиБ; stderr — 64 КиБ на вызов и 16 КиБ между вызовами;
чтение файла — страницами до 128 КиБ, список — до 500 записей, HTTP и процесс —
до 256 КиБ вывода. Превышение лимита завершает операцию и процесс с ошибкой
лимита. **Это стартовые значения из договора, не проверенные измерением;** хост
передаёт фактические значения в `initialize`, но не разрешает плагину расширить
их.

## 4. TypeScript и интерфейс окна

`node` исполняет готовый JS в закреплённом Node из поставки. TypeScript
преобразует отдельный ограниченный шаг закреплённым компилятором; встроенное
стирание типов Node не считается сборкой или проверкой типов.

`ui.entry` — готовый локальный модуль TypeScript/JavaScript из точного
`snapshotDigest`. **Будет:** внешний UI запускается только в отдельной webview,
не в iframe главного окна. У этой webview нет Tauri capabilities, `invoke`,
команд окна, файловой системы, shell, прямой сети, доступа к DOM главного окна,
другим плагинам или системному окну подтверждения. Она не может открывать новую
навигацию или новые окна. CSP запрещает удалённый код и `eval`.

Главное окно рисует доверенную рамку, имя плагина и декларативные штатные места:
пункт панели, страницу, команду палитры и кнопку. Внешняя webview рисует только
содержимое выданной области и обменивается данными через проверенные по схеме
сообщения `hoh/plugin/<id>/*`. При создании ядро выдаёт непредсказуемый
`instanceHandle`, связанный с `id`, поколением процесса и `snapshotDigest`;
старый экземпляр после обновления, выключения или падения сообщения не отправляет.

Bundled UI процесса использует ту же отдельную webview и те же ограничения:
нахождение в подписанной поставке само по себе не даёт внутренних прав. Только UI
самого ядра может компилироваться прямо в главное окно. Если доказанной изоляции
нет на конкретной платформе, вклад получает статус `blocked`, а не запускается
слабее. **Поддержка такой изоляции на всех платформах не проверена.**

## 5. Пространство `hoh/plugin/<id>/*`

**Будет:** единственное расширяемое пространство окно ↔ плагин —
`hoh/plugin/<id>/*`. При регистрации ядро проверяет одновременно:

1. `<id>` точно совпадает с владельцем активного `snapshotDigest`;
2. локальный метод объявлен в `contributes` и его сервис — в `requires.services`;
3. схемы запроса, ответа и события закрыты и прошли проверку;
4. вызывающая webview предъявила действующий `instanceHandle` того же плагина;
5. поколение процесса и `snapshotDigest` совпадают с активным экземпляром;
6. действующие права разрешают операцию в этой сессии и задаче.

Метод другого `id`, необъявленный суффикс, неизвестное поле и ответ вне схемы
отклоняются. Пространство не открывает произвольный `hoh/*`: системные методы
окна остаются закрытым протоколом ядра. Плагинный UI не может переслать Tauri
команду или `approval/request`. После обновления или выключения старые
`instanceHandle`, поколение и `snapshotDigest` отзываются до снятия вкладов.

## 6. Права

### 6.1. Пересечение четырёх наборов

Действующее право каждой операции — пересечение:

```text
одобрено плагину ∩ разрешено сотруднику ∩ разрешено задаче ∩ нужно вызову
```

Если хотя бы один набор не разрешает файл, домен, программу, секрет, сессию или
тип вклада, ядро отказывает. Плагин никогда не расширяет права сотрудника или
задачи. Проверка повторяется на каждом обратном запросе и событии, а не только
при включении.

`requestedPermissions` включает базовые права `files.read`, `files.write`,
`network.domains`, `programs` и отдельные права:

- `conversation.read` — получать текст только текущей сессии текущей задачи;
  другая сессия требует отдельного точного grant (выданного доступа), без
  шаблонов и права «все сессии сотрудника»;
- `hooks` — точный список событий; защитный хук не получает право менять данные;
- `prompt` — отдельно `section`, `context`, `assemble`; чтение переписки не
  следует из права добавить статический раздел;
- `executor.register` и более сильное `executor.replace`;
- `ui` — точные виды `panelItem`, `page`, `paletteCommand`, `button`;
- `replace` — точный список слотов вида `<kind>:<slot>` без `*`; каждое
  `replaces` вклада обязано входить в этот список.

Права на вклад и доступ к данным независимы. Например, кнопка не даёт права
читать разговор, а хук `tools/pre-execute` не даёт права читать файл из его
аргументов через брокер.

### 6.2. Включение, обновление и откат

Установить инертный снимок может человек или агент. Установка принимает только
готовый результат `hoh plugin pack`, ничего не собирает, не запускает менеджер
пакетов, компилятор или код плагина и прав не выдаёт. **Будет:** включить плагин
может только человек:

1. действие начинается в главном окне;
2. окно показывает `id`, версию, источник, `snapshotDigest`, все вклады, замены,
   запрошенные и выдаваемые права;
3. отдельное системное окно подтверждает точное действие;
4. ядро связывает решение MAC с действием и точным `snapshotDigest`;
5. только после проверки MAC публикуются вклады.

Агент, модель, процесс плагина и его UI не имеют пути подтверждения. Любой новый
`snapshotDigest` — новое подтверждение, даже при той же версии и правах. Пока
обновление ждёт решения, работает прежний одобренный снимок. Откат — повторное
включение старого снимка и тоже требует подтверждения. Версия сохранённой задачи
не переключается молча: она закрепляет `{id, version, snapshotDigest}`.

При этом авторская пара `{id, version}` неизменяема: другой `digest` под ней
отклоняется, а не предлагается человеку как обновление. Новый авторский набор
обязан иметь новую версию. Повторное подтверждение относится к новому
`snapshotDigest` новой версии либо к явному откату на уже известный снимок.

Выключение сразу отзывает права, отменяет операции и снимает вклады. Расширение
прав или изменение заменяемых частей требует нового подтверждения. Сокращение
прав не может разрешить новое действие.

## 7. Песочница процесса

**Будет:** `process`, `node` и каждый их потомок видят только:

- неизменяемый снимок плагина на чтение;
- отдельную пустую временную папку текущего вызова на запись;
- stdin/stdout/stderr протокола.

Папки пользователя внутрь не монтируются. Файлы доступны только через
`host/fs.*`; сеть закрыта ОС и доступна только через `host/http.request`; запуск
программ — только через `host/process.run`. Окружение задаёт хост, без `LD_*`,
`NODE_*`, секретов и домашней папки пользователя. Закрываются посторонние
дескрипторы, ptrace, доступ к процессам и `/proc` хоста; задаются пределы памяти,
процессов, файлов, времени и вывода. Если обязательная изоляция недоступна,
процессный плагин получает статус `blocked`, а не запускается слабее. `skill` —
исключение, потому что кода не исполняет.

Эта песочница процессов не заменяет UI-изоляцию § 4. Webview не наследует право
процесса на брокер и требует собственные схемы сообщений, `instanceHandle` и
отзыв поколения.

**Сегодня:** `crates/hoh-sandbox-local/src/profiles.rs` использует bubblewrap или
Landlock, отдельный PID namespace и ограничения записи, но монтирует весь `/` на
чтение (`--ro-bind / /`; Landlock также выдаёт read-only `/`). Это честно не
соответствует описанной песочнице плагинов. Нужен новый отдельный профиль; до него
первым безопасным видом для реализации будет MD. Внешнего установщика
HOH-42 сегодня нет даже для MD.

## 8. Что остаётся только в Rust-ядре

Следующие механизмы не экспортируются процессам и не заменяются обычным плагином:

- fiber и его жизненный цикл;
- основной загрузчик, проверка манифеста и сборка неизменяемого снимка;
- брокер прав и вычисление пересечения прав;
- формирование, хранение и проверка MAC подтверждений;
- файловый, сетевой, программный и секретный брокеры;
- запуск и контроль песочницы;
- проверка JSON-RPC, схем, поколений, идентичности владельца и лимитов.

Обычный плагин может заменить прикладные части поверх этой границы: инструменты,
исполнитель инструментов, навыки, промпт, шаги агента, защитные правила в сторону
запрета, внешний исполнитель и интерфейс. Он не может заменить сам механизм,
который выдаёт права и решает, считать ли подтверждение настоящим.

Полная замена реализации подтверждений, песочницы или другого пункта списка
разрешена только проверенному `rust-inproc` из подписанной сборки HoH. Такой
компонент компилируется с продуктом, связывается по устойчивому `key` и проходит
релизное ревью. Внешний Rust-бинарник `process`, Go и TypeScript этого права не
получают ни при каком наборе пользовательских разрешений.

Переход `process` → `rust-inproc` не автоматический и не обещает побайтовое
совпадение. Он может потребовать отдельный адаптер к внутреннему Rust API и всегда
проходит новое security/release review (проверку безопасности и выпуска).

## 9. Цепочка поставки

### 9.1. TypeScript и UI

Сохраняется политика HOH-26:

- все прямые и транзитивные версии точные, lock-файл содержит хеши;
- один реестр; git- и URL-зависимости запрещены;
- версия выдерживается не меньше 7 суток;
- install/preinstall/postinstall/prepare и любые исключения для build-скриптов
  запрещены;
- `binding.gyp`, нативные модули, FFI, скачивание бинарников и Node пользователя
  запрещены;
- разрешённый шаг получения зависимостей идёт с сетью, но без секретов, только из
  `registry.npmjs.org`, с проверкой имени, версии и хеша;
- `hoh plugin pack` отдельно и офлайн собирает с frozen lock-файлом и без
  скриптов готовый JS и проверенное дерево зависимостей;
- установка не запускает pnpm, TypeScript, build-скрипты или иной код и принимает
  только уже готовый artifact (набор файлов).

Выдержка и хеш уменьшают риск, но не доказывают добросовестность кода. При выдаче
файла и домена окно предупреждает, что плагин сможет отправить разрешённые данные
на разрешённый сайт.

### 9.2. Rust и Go

Внешние Rust/Go-плагины устанавливаются готовыми бинарниками для точного
`execution.target`; на машине пользователя они не собираются. Авторский `digest`
и установленный `snapshotDigest` обязательны и проверяются до каждого запуска.
Исходники могут лежать рядом для аудита, но исполняется только файл из одобренного
снимка. `rust-inproc` входит только в подписанную сборку продукта.

Подпись издателя стороннего плагина и публичный каталог **сегодня отсутствуют и
не специфицированы**. Хеш доказывает неизменность, но не личность или качество
автора. До отдельного решения временно разрешённые источники — папка человека и
короткий проверенный список; они не доказывают доверие. Офлайн-установка возможна
из заранее полученного снимка.

## 10. Пользовательский плагин → встроенный

Для bundled `skill`, `process` и `node` путь состоит в переносе того же
`hoh-package.json` и готового набора в подписанную поставку HoH. Если каноническая
копия побайтово та же, её `snapshotDigest` не меняется; любая пересборка создаёт
новый снимок. Вклад становится штатной строкой состава, но код продолжает
работать через ту же песочницу, UI-изоляцию и протокол. Переписывать API плагина
не нужно.

`rust-inproc` — отдельное глубокое встраивание: реализация компилируется с
продуктом, а `execution.key` связывается с Rust `PluginDef`. Оно может потребовать
адаптер; сохранение манифеста, `id`, настроек, вкладов и правил замены является
целью, но не автоматическим преобразованием готового внешнего бинарника.

Встроенный статус не означает скрытых прав. Любая процессная встроенная часть
остаётся в брокерах и песочнице. Дополнительные полномочия получает только явно
проверенный `rust-inproc`, которому их выдала подписанная сборка.

## 12. Непроверенное и решения до реализации

- **Нормативно выбрано:** внешний UI работает только в отдельной webview без
  Tauri capabilities. iframe главного окна не является допустимым вариантом.
  Реализуемость и изоляцию этой webview надо доказать отдельно на каждой
  поддерживаемой ОС; без доказательства вклад получает `blocked`.
- **Продуктовые решения:** какие UI-слоты ядро объявляет заменяемыми; размеры и
  возможности страниц; личность издателя, публичный каталог, отзыв опасного
  снимка и формат доверенного списка; может ли first-party bundled plugin без
  прав на данные включаться вместе с поставкой.
- **Инженерные измерения:** точные таймауты каждого класса хуков, размеры кадров,
  память и остальные численные лимиты. Они не являются решениями основателя;
  обязательная политика отказа уже задана в § 3.4.
- Поддержка внешнего UI и протокола v2 ещё не проверена сквозным прототипом.
- Чтение пользовательского слоя патчей именно запуском окна не проверено. Код
  умеет подключать слой при `user_layer` —
  `crates/hoh-loader/src/profile.rs:218-235`, но фактический путь запуска окна в
  этой работе не исполнялся.

## 13. Путь автора на одной странице

Весь путь ниже — **предложение; в коде его нет**.

1. `hoh plugin new --language md|typescript|rust|go` создаёт манифест и один
   основной файл.
2. Автор описывает вклады и права в манифесте и связывает их `id` с короткими
   обработчиками.
3. `hoh plugin pack` закреплёнными инструментами собирает `dist/` или `bin/`,
   проверяет схемы, зависимости и права, затем сам вычисляет `digest`.
4. `hoh plugin inspect` простыми словами показывает все вклады, права и замены.
5. `hoh plugin install` инертно проверяет и копирует готовый набор; ничего не
   собирает и не исполняет.
6. `hoh plugin enable` открывает отдельное системное окно, где человек подтверждает
   точный снимок.

Предлагаемые имена будущих SDK: `@alexandrie/hoh-plugin-sdk` для TypeScript,
`hoh-plugin-sdk` для Rust и `alexandrie.dev/hoh/plugin-sdk` для Go. Имена и API
ещё не приняты и в коде отсутствуют. SDK должен скрывать JSON-RPC, регистрацию,
отмену и поколения, оставляя автору модель `serve(manifest, handlers)`. MD SDK не
нужен.
