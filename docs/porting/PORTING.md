# Правила переноса DeepSeek Harness (TypeScript) в HoH (Rust)

Обязательны для каждого исполнителя и ревьюера. Образец: `/mnt/toshiba/alexandrie/hoh/refs/deepseek-harness`,
коммит `39163dd3`. Образец только читается: в нём ничего не запускается, не собирается и не меняется.
Всё о ядре (сервисы, события, эффекты, зависимости, конфигурация плагина, таймеры, отмена) — в
`docs/kernel.md`, раздел с таблицей «TypeScript → Rust»; здесь оно не повторяется.

## 1. Главное правило

Переносится **поведение**, а не текст. Результат — обычный Rust, который делает то же, что образец, во всём,
что видно снаружи пакета: модели, журналу сессии, файлам, протоколам, конфигурации, вызывающему коду.
Внутреннее устройство может отличаться, если так проще и надёжнее на Rust.

Нельзя улучшать, дополнять и «заодно исправлять» образец. Подозрение на ошибку в образце записывается
в `PORT_NOTES.md` и переносится как есть, если ревьюер и ведущий не решили иначе.

## 2. Единица работы

Один пакет dsh — один crate. Имя и каталог берутся из `docs/porting/MAP.tsv` (столбец `hoh_crate`).

```
crates/hoh-<имя>/
  Cargo.toml        зависимости только через `workspace = true` и `path` на crates из задания
  src/lib.rs        модули повторяют файлы `src/*.ts` образца (snake_case)
  tests/*.rs        по одному файлу на `tests/*.spec.ts` образца
  locale/*.json     копия без изменений, если есть в образце
  PORT_NOTES.md     учёт переноса (раздел 12)
```

Если в пакете образца есть свой `LICENSE` или в коде и README сказано, что часть взята из другого проекта,
файл лицензии копируется в crate без изменений, а в отчёте это названо отдельной строкой: ведущий дополняет `NOTICE`.

Дополнительные точки входа пакета (`exports` в `package.json`, например `./pipeline`) становятся публичными
модулями. Ничего вне своего crate исполнитель не меняет: ни корневой `Cargo.toml`, ни чужие crates, ни документы.
Нужна новая сторонняя библиотека или изменение чужого crate — остановиться и написать ведущему.

## 3. Имена

| В образце | В Rust |
|---|---|
| тип, класс, интерфейс `ToolExecutor` | то же имя `ToolExecutor` |
| функция, метод, поле `resolveSpec` | `resolve_spec` |
| константа `SESSION_FORMAT_VERSION` | то же имя |
| файл `json-schema.ts` | модуль `json_schema` |

Не меняются никогда, до байта: имена событий (`agent/pre-step`), имена инструментов, коды ошибок,
ключи конфигурации, теги и поля JSON в журнале и протоколах, имена сервисов в конфигурации, имена пакетов dsh.
Для полей JSON это задаётся атрибутами serde (`rename_all = "camelCase"` или `rename`), а не именами полей Rust.

## 4. Типы и данные

- Непрозрачный идентификатор (`Branded<...>`) — свой тип-обёртка над `String` с `#[serde(transparent)]`,
  объявленный макросом `hoh_brand::branded_string!`. Голый `String` для идентификатора на границе пакета запрещён.
  Идентификатор, который образец объявляет в двух пакетах (`SessionId` в `llm` и в `core/session`), объявляется
  один раз в `hoh_brand::ids` и реэкспортируется владельцами: два вызова макроса дают два несовместимых типа.
- Закрытое размеченное объединение — `enum` с `#[serde(tag = "...")]`; `match` без ветки `_`
  (так переносится `assertNever`).
- Расширяемое объединение или карта, которые в образце дополняются из других пакетов через declaration merging
  (`SessionEventMap`, карты событий, поиска, ресурсов): владелец хранит запись в общем виде (тег и сырой JSON),
  расширяющий пакет объявляет свой тип с константой-тегом. Общий `enum` со списком чужих вариантов запрещён.
- `undefined` — поле отсутствует: `Option<T>` с `skip_serializing_if = "Option::is_none"`. `null` — явный `null`.
  Где образец различает оба случая, различает и перенос.
- Порядок полей структуры повторяет порядок, в котором образец собирает объект. Произвольный JSON —
  `serde_json::Value` с сохранением порядка ключей.
- Аргументы инструмента остаются сырой строкой JSON до места, где их разбирает образец.
- Числа: счётчики и размеры — `u64`, отметки времени в миллисекундах — `i64`. `f64` только для величин,
  дробных по смыслу. Целое значение не должно оказаться в JSON как `1.0`: JavaScript пишет `1`.
- `Map` и `Set` образца хранят порядок вставки. Если порядок виден снаружи (модели, журналу, тесту) —
  `IndexMap`, `IndexSet`. `HashMap` только когда порядок не наблюдается. `BTreeMap` только там, где образец сортирует.
- Длина строки в образце считается в единицах UTF-16. Если от длины зависит видимый результат (обрезка,
  лимит, смещение), перенос считает так же (`encode_utf16().count()`) и не режет символ посередине.
  Считать байты UTF-8 вместо этого — ошибка: русский текст даст другой результат.
- Сортировка строк по умолчанию в JavaScript идёт по единицам UTF-16; `localeCompare` зависит от локали —
  каждое такое место записывается в `PORT_NOTES.md`.
- Значение, подставленное в текст (`${value}`, `String(value)`, сообщение об ошибке), выглядит как в JavaScript:
  `hoh_util_values::js_string` для произвольного JSON (объект — `[object Object]`, массив — элементы через запятую)
  и `js_number_string` для числа (`1e21`, `0.000001`, `1e-7`, целое без `.0`). `format!("{value}")` для `Value`
  и для `f64` в видимом тексте запрещён.
- Текст JSON, который видят модель, журнал сессии, stdout, протокол или файл (`JSON.stringify` образца), пишет
  `hoh_util_values::js_json_stringify` (и `js_json_stringify_pretty` для `JSON.stringify(x, null, n)`): числа в
  записи JavaScript (`1`, а не `1.0`; `100000000000000000000`, а не `1e20`), ключи-целые впереди по возрастанию.
  Структура сначала переводится в `Value` (`serde_json::to_value`). `JSON.parse` образца — `js_json_parse`: числа и
  порядок ключей как в JavaScript, глубина вложенности не ограничена 128 уровнями, текст ошибки как у V8.
  `serde_json::to_string`, `to_writer` и `from_str` для таких текстов запрещены; внутри тестов и для данных,
  которые не покидают процесс, они допустимы.
- Рекурсия по `Value` допустима: `js_json_parse` не принимает вложенность глубже 4096 уровней
  (`JS_JSON_MAX_DEPTH`; сам JavaScript не может записать глубже примерно 4174), а потоки приложения получают
  стек 64 МиБ. Собирать кодом значение глубже этого нельзя. Рекурсия по структуре, длина которой ничем не
  ограничена (цепочка `previous` в chunked-list, список событий), запрещена: только цикл.
- Число из JSON приводится к целому только точно: `as_u64()` либо проверка, что `f64` целое, неотрицательное и
  в пределах 2^53. Приведение `as u64` от `f64` молча превращает `-1` в `0` и `2.5` в `2` — там, где образец
  по такому ключу ничего не находит и сообщает об ошибке.
- Время в виде строки — формат `toISOString()`: `2026-01-02T03:04:05.678Z`, всегда три знака миллисекунд.
- Пути: где образец использует собственные пакеты (`util/workspace-path`, `util/home-paths`), перенос использует
  их перенесённые версии, а не `std::path` напрямую. Пути, видимые модели, сохраняют вид образца.
- Регулярные выражения: crate `regex`. В JavaScript без флага `u` классы `\d`, `\w`, `\b` работают только
  с ASCII, а в `regex` по умолчанию с Unicode: писать `(?-u:\d)` или явный класс. Выражение с заглядыванием
  или обратной ссылкой переписывается кодом; если нельзя — вопрос ведущему.
- То, что Node и JavaScript делают сами, воспроизводится общими помощниками, а не заново в каждом crate.
  Каждый из них проверен по образцу, снятому с Node 22.23.1 (`tests/fixtures` их crates):
  - **Пробельные символы.** `trim()`, `trimStart()`, `trimEnd()` и `\s` JavaScript — это
    `hoh_util_values::{js_trim, js_trim_start, js_trim_end, is_js_white_space}` и класс
    `JS_WHITE_SPACE_SET` для `regex`. `str::trim`, `char::is_whitespace`, `split_whitespace` и `\s` crate
    `regex` считают иначе: U+FEFF пробел только в JavaScript, U+0085 и U+001C–U+001F только в Rust. Файл с
    BOM в начале даёт разный результат.
  - **Пути `path`.** `join`, `normalize`, `resolve`, `relative`, `dirname`, `basename`, `extname`,
    `isAbsolute` — это `hoh_util_workspace_path::node_path::*` над строками. `Path::join`, `Path::parent`,
    `Path::components` дают другое: `join('/x//y', 'a')` в Node — `/x/y/a`, `dirname('/')` — `/`,
    `dirname('/a/.')` — `/a`. `std::path` годится там, где путь только передаётся системе и никуда не пишется.
  - **Порядок `readdir`.** `readdir` Node (обычный и с `withFileTypes`, без `recursive`) на Unix отдаёт имена
    отсортированными по байтам; `opendir`/`Dir.read` — в порядке системы. `read_dir` в `std` и `tokio` не
    сортирует: перенос `readdir` обязан отсортировать имена по байтам до любого обхода.
  - **Тексты системных ошибок.** Сообщение ошибки `fs` в Node — `ENOENT: no such file or directory, open
    '/x'`, запуска процесса — `spawn cmd ENOENT`. Там, где образец показывает `error.message` или сверяет
    `error.code`, перенос строит текст через `hoh_error::{node_fs_error_message, node_spawn_error_message,
    node_error_code}`; `Display` у `io::Error` (`No such file or directory (os error 2)`) в видимый текст не идёт.
    Какое слово (`open`, `scandir`, `copyfile`, …) Node ставит для какой функции — таблица в
    `crates/hoh-error/PORT_NOTES.md`.

## 5. Текст, который видит модель или пользователь

Системные промпты, имена и описания инструментов, описания параметров, JSON Schema инструментов, тексты
результатов и ошибок инструментов, напоминания — копируются **до байта**. Их нельзя переводить, сокращать,
переформатировать. JSON Schema инструмента строится перенесённым построителем или хранится готовой
константой; автоматический вывод схемы из типа Rust для видимых модели схем запрещён.

Каталог `locale/` копируется без изменений. Механизм локализации не изобретается: читается только то,
что читает образец.

## 6. Асинхронность и состояние

- `Promise` — `async fn` на tokio. `Promise.all` — `try_join_all` с сохранением порядка результатов,
  `Promise.race` — `tokio::select!`. Внутри плагина нет `block_on` и блокирующего ввода-вывода
  (`tokio::fs`, `tokio::process`, для тяжёлого счёта `spawn_blocking`).
- JavaScript однопоточен: код между двумя `await` неделим. В Rust это свойство нужно сохранить явно.
  У изменяемого состояния плагина один владелец: либо задача-актор с очередью сообщений, либо `std::sync::Mutex`
  с короткой секцией. Блокировка не удерживается через `.await`. Последовательность «проверил — изменил»,
  которая в образце была синхронной, выполняется под одной блокировкой.
- `AbortSignal` и `AbortController` образца — `hoh_timeout::AbortSignal` и `AbortController`: отмена с причиной.
  `signal.reason` — `signal.reason()`; `signal.throwIfAborted()` — `signal.throw_if_aborted()?`; причина —
  общее значение ошибки `hoh_error::SharedError`: `reason instanceof X` — `downcast_ref::<X>()`,
  `error === signal.reason` — `ptr_eq`. Отмена без названной причины несёт `AbortError`. Свои типы сигнала
  (`watch`, `bool`, голый `CancellationToken` в параметрах функций) запрещены.
- Таймеры, потоки значений, освобождение ресурсов — по `docs/kernel.md`. Прямые `tokio::time::sleep`
  и `tokio::spawn` в коде плагина запрещены, если образец пользуется средствами контекста: иначе работа
  переживёт выгрузку плагина.
- Глобального изменяемого состояния нет: никаких `static` с реестрами. Всё живёт в контексте и сервисах.
  Единственное исключение — счётчик выдачи уникальных идентификаторов (`static AtomicU64`, только
  `fetch_add`): он ничего не хранит и влияет лишь на то, что значения различны.

## 7. Ошибки

- Ошибка с кодом — всегда значение одного типа `hoh_error::HarnessError` (`name`, `code`, `message`, причина,
  необязательные типизированные данные) с тем же кодом, именем и текстом, что в образце. Маршрутизация идёт по коду,
  не по тексту. Типов-обёрток над `HarnessError` нет: иначе ошибку нельзя узнать за `Box<dyn Error>`.
- Класс-наследник образца (`class JobError extends HarnessError`) переносится пустой структурой с константой имени
  и конструктором, который возвращает `HarnessError`:
  `pub struct JobError; impl JobError { pub const NAME: &str = "JobError"; pub fn new(message, code: JobErrorCode) -> HarnessError }`.
  Набор кодов наследника — `enum` с `as_str()`. Дополнительные поля наследника — отдельная структура данных,
  прикреплённая через `with_detail` и читаемая через `detail::<T>()`.
- `e instanceof HarnessError` → `HarnessError::of(&e)`; `e instanceof JobError` → `e.is_named(JobError::NAME)`;
  `e.code === 'X'` → `e.code() == "X"`. Причина любого типа передаётся в `with_cause`.
- Функция, которая в образце бросает только ошибки с кодом, возвращает `Result<T, HarnessError>`; которая может
  бросить что угодно — `Result<T, hoh_error::BoxError>`. Класс образца, который наследует простой `Error`,
  переносится обычным типом ошибки crate.
- Собственные ошибки crate — `enum` с `thiserror`. `anyhow` в библиотечных crates запрещён.
- Ожидаемый отказ — значение `Err`, не паника. `unwrap`, `expect`, `panic!`, `unreachable!` вне тестов
  допустимы только для доказанного инварианта с комментарием в одну строку.
- `todo!()`, `unimplemented!()` и пустые заглушки в сданной работе запрещены. Не сделано — значит
  записано в `PORT_NOTES.md` и названо в отчёте.
- Неверная конфигурация — отказ при загрузке с понятным текстом, как в образце. Тихий пропуск запрещён.

## 8. Чего в переносе нет

- Обращения к Typert (`@Remote`, `@RemoteScope`, `TypertRemoteService`, `bindTypertRemote`, расширения карт
  `dsh-typert-protocol`): транспорт их окна не переносится. Метод остаётся обычным публичным методом сервиса.
  Над ним ставится строка `/// Remote: <namespace>.<method>` — по этим строкам позже собирается протокол
  нашего приложения. Больше ничего от Typert не переносится.
- `Proxy`, `Symbol`-трюки, declaration merging как механизм, динамический `import()`, замена кода на лету,
  `!!js` в конфигурации, проверки сборки npm (`exports.built.e2e.ts`, `publint`), генераторы документации.
- `unsafe` запрещён линтом. Системные вызовы — через безопасные обёртки из `docs/porting/DEPS.md`.
  Без `unsafe` не обойтись — вопрос ведущему до написания кода.
- `println!`, `eprintln!`, `dbg!`: только журнал через контекст. `std::process::exit` — только в `apps/*`.
- Переменные окружения читаются там же и так же, как в образце.

Ветки по платформе (`process.platform`) переносятся все, через `cfg`. Ветки Windows и macOS, которые пока
нечем проверить, перечисляются в `PORT_NOTES.md` как непроверенные. Исключение: ветка, которая вызывает
пакет этапа 5 (`win32-process`, `sandbox-windows-acl`, `pwsh-*`), до этапа 5 не пишется и записывается
в «Не перенесено» со словами «ждёт этапа 5».

## 9. Конфигурация плагина

Схема конфигурации образца (`schemastery`, `zod`) становится структурой с serde по правилам `docs/kernel.md`.
Ключи, значения по умолчанию, допустимые значения и тексты отказов совпадают с образцом: файлы конфигурации
dsh должны загружаться без правок. Настраиваемое в образце остаётся настраиваемым; новых настроек нет.

## 10. Тесты

- Каждый `tests/<имя>.spec.ts` переносится в `tests/<имя>.rs`. Каждый случай `it('...')` становится тестом
  с тем же смыслом и узнаваемым именем. Проверки не ослабляются и не удаляются ради прохождения.
- Не переносятся и перечисляются в `PORT_NOTES.md` с причиной: проверки типов TypeScript (`*-types.spec.ts`),
  проверки собранного пакета npm, проверки генераторов, тесты на замену кода на лету, тесты с настоящим
  ключом API (`*.e2e.ts`), тесты окна.
- Тест не ходит в сеть, работает во временном каталоге, не зависит от настоящего времени
  (`tokio::time::pause`) и от порядка запуска.
- Помощники из `packages/test-support` берутся из их перенесённых crates, названных в задании.
- Тест, который в образце выглядит неверным, переносится как есть и записывается в вопросы ведущему.

## 11. Что разрешено запускать

Исполнитель-писатель: `cargo fmt -p <crate>`, `cargo build -p <crate>`, `cargo clippy -p <crate>`,
`cargo test -p <crate>` — с каталогом сборки из задания (`CARGO_TARGET_DIR`), чтобы не ждать чужую сборку.
Больше ничего: никаких установок, серверов, браузеров, сети, git-команд, меняющих состояние.

Ревьюер только читает: сверяет Rust с TypeScript и ничего не запускает.

## 12. PORT_NOTES.md

```
# hoh-<имя> ← <путь пакета в dsh> @ 39163dd3

## Файлы
| образец | перенос | состояние |

## Отличия от образца
Каждое намеренное отличие поведения или публичного API и его причина.

## Не перенесено
Что именно и почему (правило раздела 8 или 10, либо решение ведущего).

## Не проверено
Ветки платформ и случаи, которые не покрыты тестом.

## Вопросы ведущему
```

Публичный символ, которого нет в образце, допустим только с записью в «Отличия от образца».

## 13. Отчёт исполнителя

Коротко и по фактам: какие файлы образца перенесены; команда и итог тестов (число пройденных и упавших);
что не перенесено и почему; вопросы. Слова «готово» без строки с итогом `cargo test` недостаточно.

## 14. Что проверяет ревьюер

1. Каждый экспортируемый символ образца имеет пару или запись в `PORT_NOTES.md`.
2. Ветвления, граничные случаи и порядок побочных действий совпадают с образцом.
3. Тексты и схемы из раздела 5 совпадают до байта; имена из раздела 3 не изменены.
4. Формат JSON: имена, порядок, отсутствие поля против `null`, вид чисел.
5. Освобождение ресурсов: всё зарегистрированное снимается при выгрузке; нет работы, переживающей плагин.
6. Гонки: состояние с одним владельцем, нет блокировки через `.await`.
7. Тесты образца перенесены полностью, проверки не ослаблены.
8. Нет ничего сверх образца.

Замечание ревьюера содержит место в Rust, место в TypeScript, наблюдаемое расхождение и его последствие.
