## Отличия от образца
- Значения JSON — `serde_json::Value` (с `preserve_order`). Поэтому `isJsonValue`/`snapshotJsonValue` проверяют только то, что
  в `Value` ещё возможно нарушить: отрицательный нуль (`-0.0`). Циклы, разреженные массивы, символы, функции, экземпляры
  классов, чужие области выполнения (`hasIntrinsicConstructor` и т. д.) в Rust невозможны. Проверка `is_json_value` итеративна, как в образце. `snapshot_json_value` копирует через `Value::clone`, то есть рекурсивно
  (образец обходит итеративно). Для разобранного входа это безопасно: `serde_json` отказывает во вложенности глубже 128 при разборе.
  Значение, собранное программно и глубже, остаётся на ответственности вызывающего.
  `snapshot_json_value` возвращает копию (`Option<Value>`); обобщённого `<T>` нет.
- `deep_equal_json` сравнивает числа по значению (`1` равно `1.0`): в JavaScript один числовой тип. Порядок ключей не важен.
  Образец проверяет ключи через `key in right`, то есть и по цепочке прототипов; в `Value` прототипа нет.
- Числа в разобранном тексте: целое значение после `JSON.parse` в образце печатается как `1`, а `serde_json` разбирает `-1e3`
  как `f64` и печатает `-1000.0`. Разобранные значения с целой дробной частью и модулем меньше 2^53 приводятся к целому
  (PORTING 4). Значение `-0` разбирается как `0`.
- `PartialArguments`: методы `&mut self` (читатели сканируют текст и запоминают ответы); `invalid`, `closed`, `keys` — методы,
  а не свойства. `is_sealed(&self)` не может сканировать по типу.
- `PartialArguments.EMPTY` — функция `PartialArguments::empty()`, каждый вызов даёт свой запечатанный вид (общий `static` запрещён, раздел 6).
- `append` возвращает `Result<(), SealedViewError>` вместо исключения; текст ошибки: `PartialArguments: cannot append to a sealed view`.
  Новый публичный тип `SealedViewError` (thiserror).
- `settle(&mut self, text) -> Option<PartialArguments>`: `None` — тот же вид запечатан на месте (образец возвращает `this`),
  `Some(view)` — новый запечатанный вид, исходный не изменён.
- `fromObject(unknown)` → `from_object(&Value)`; не объект — вид без полей. Вызов с `undefined` невозможен.
- Тексты. Образец считает длины и смещения в единицах UTF-16, как и перенос; хранение — `Arc<[u16]>`. Ответ может содержать
  одинокий суррогат (префикс, оборванный посреди пары). Поэтому для `text` и `textPrefix` есть пары: `text_utf16`,
  `text_prefix_utf16` (точные единицы) и `text`, `text_prefix` (`String`, одинокий суррогат заменён на U+FFFD).
  Ключи полей хранятся как UTF-16; `keys()` отдаёт `String` с той же заменой (для объектного вида ключи точные).
- `append` принимает `&str`: фрагмент не может заканчиваться одиноким суррогатом (в JavaScript поток может оборвать пару).
- `LengthReadOptions { step: Option<f64>, offset: Option<f64> }` оставлен дробным, потому что образец делает `floor` и тестирует `2.9`.
  `string_exceeds` и `text_prefix` принимают `usize`; «не меньше нуля/единицы» сохранено (`text_prefix` берёт `max(1, n)`).
- `#[doc(hidden)] json_parse_count()` — счётчик разборов JSON на одном виде. Нужен только затем, чтобы перенести проверки
  образца «ничего не разбирается, пока не попросили», которые там сделаны шпионом на `JSON.parse`. Символа в образце нет.
- Идентичность разобранного значения (`Object.is` на объектах в `refresh`) заменена номером записи: контейнер считается
  изменившимся, только если поле перезаписано новой записью, как и в образце.
- Равенство видов (`PartialEq`) сравнивает только источник (фрагменты, объект, флаг запечатанности), как `toEqual` по перечислимым полям.
- Добавлены `js_number_string(f64)` и `js_string(&Value)`: порт поведения среды выполнения JavaScript, на которое опирается образец
  (шаблонные строки и `String(value)` в сообщениях об ошибках и результатах инструментов). В `index.ts` их нет. `js_number_string` —
  `Number::toString(10)`: цифры берутся из кратчайшей записи Rust (`{:e}`), затем применяется правило раздела 6.1.6.1.20 ECMAScript
  (десятичная запись при показателе от -6 до 20, иначе `e+`/`e-`). `js_string` — `String(value)`: `null`, булевы, число через
  `js_number_string`, строка без кавычек, массив через `,` (`null` — пустая строка), объект `[object Object]`.
- Добавлены `js_json_stringify`, `js_json_stringify_pretty(value, indent)` и `js_json_parse(text)` с типом ошибки `JsonParseError`
  (`message()`, `Display`): `JSON.stringify` и `JSON.parse` как их выполняет V8 над `serde_json::Value`. Обход в обе стороны идёт
  с явным стеком, глубина вложенности не ограничена стеком вызовов (тест: 4000 уровней в потоке со стеком 256 КиБ; при ошибке
  разбора, при замене значения повторным ключом и при лишнем тексте после готового значения все значения, которые могли бы
  оказаться глубокими, разбираются итеративно; остальные выходы разбора такие значения не отбрасывают). Запись: целые до 2^53 как есть, большие `i64`/`u64` как ближайшее
  `double` (`9007199254740993` → `9007199254740992`, `u64::MAX` → `18446744073709552000`), дробные через `js_number_string`,
  `-0` как `0`; ключи-индексы (`0`…`4294967294`, канонические) впереди по возрастанию, остальные в порядке хранения; строки
  экранируются как у `JSON.stringify`; отступ ограничен 10. Разбор: грамматика `JSON.parse`; каждое число сначала `double`,
  целое до 2^53 (кроме `-0`) хранится целым, `-0` как `-0.0`; повтор ключа сохраняет первую позицию и последнее значение.
  Различия: (а) литерал, переполняющий `double` (`1e400`), хранится как `Value::Null` (`Value` не вмещает Infinity, JavaScript печатает
  его `null`); (б) экранированный одиночный суррогат (`"\ud800"`) в строке даёт U+FFFD, пара даёт символ; то же для одной единицы
  UTF-16, которую V8 цитирует в сообщении (`'\ud83d'` для источника `😀` становится U+FFFD); (в) сообщения проверены только по
  Node 20 (V8 11.3), Node 22 и новее добавляют к сообщениям с позицией суффикс ` (line L column C)`, его здесь нет: известное
  расхождение с Node 24, на котором работает образец. Правила сообщений восстановлены по фикстуре: без подробного сообщения V8
  называет токен (`Unexpected token 'x', "…" is not valid JSON`, источник от 21 единицы UTF-16 цитируется отрезком в 10 единиц
  вокруг позиции с `...` с нужной стороны, особые источники `NaN`, `Infinity`, `undefined`, `[object Object]` без токена);
  подробные сообщения: имя ключа, `,`/`]`/`}`, строки, числа; двоеточие после второго и следующих ключей не получает подробного
  сообщения; обратная косая черта в конце текста или перед символом за пределами Latin-1 даёт сообщение о токене. Позиции в
  единицах UTF-16. Фикстуры: `tests/fixtures/js_json_roundtrip.jsonl` (2088 строк), `tests/fixtures/js_json_parse_errors.jsonl`
  (1799 строк), генератор `tests/fixtures/gen-js-json.mjs`.
- Предел вложенности разбора: `pub const JS_JSON_MAX_DEPTH: usize = 4096`. Массивы и объекты глубже этого предела (считая и пустые)
  дают `JsonParseError` с сообщением `Maximum call stack size exceeded`; глубина 4096 разбирается, 4097 — отказ. Намеренное отличие:
  в Node 20 у `JSON.parse` практического предела нет, а `JSON.stringify` и любой рекурсивный код JavaScript останавливаются примерно
  на 4174 уровнях с перехватываемой `RangeError`. В Rust переполнение стека обрывает процесс, а текст может прийти от модели
  (аргументы инструмента); предел делает безопасной рекурсию по разобранному `Value` в остальном коде. Разбор и запись по-прежнему
  идут с явным стеком; у `js_json_stringify` своего предела нет.
- Порядок ключей: JavaScript ставит целочисленные ключи объекта первыми по возрастанию. Перенос повторяет это для объектного вида
  (`keys`, вложенные объекты, возвращаемые `value`) и для разобранных значений. `{"2":0,"1":0}` даёт ключи `["1","2"]`,
  сериализация `{"1":0,"2":0}`. Тесты: `orders_integer_like_keys_ascending_...`.
- Шаг `NaN` в `LengthReadOptions::step` сохраняется как `NaN` (как `Math.max(1, NaN)`); чтения длины тогда не сообщают об изменении.
  Вызывающих `stringLength` вне пакета в образце нет, значения шага в тестах образца целые и `2.9`; тип `f64` оставлен ради `2.9`.
  Тест: `keeps_a_nan_step_...`.
- `{"x":1e999}`: JavaScript читает `Infinity`, здесь значение неверно (`value` = `None`, `invalid` = true, `complete("x")` = false).
- Вложенность глубже 128: `{"x":` + 129 вложенных массивов с `0` — JavaScript читает массив, здесь `serde_json` отказывает, как выше.
- Полное значение с одиночным суррогатом: `{"x":["\ud800"]}` — JavaScript сохраняет суррогат, здесь значение неверно (как выше).
  Строка верхнего уровня `{"x":"\ud800"}` разбирается своим декодером: `text_utf16` даёт `[0xd800]`, `text` — U+FFFD.
  Ключ `{"\ud800":"x"}`: `keys()` отдаёт `"\u{fffd}"`, и найти по нему поле нельзя (в JavaScript можно).
- `-0` и `0`: `{"n":-0}` в JavaScript читается как `-0`, здесь как `0`; повторный `"n":-0` после наблюдения `0` в `refresh` даёт true в
  JavaScript и false здесь.
- Целые больше 2^53: `9007199254740993` точно здесь, в JavaScript округляется до `9007199254740992`; `refresh` при замене
  `9007199254740992` на `9007199254740993` даёт true здесь и false в JavaScript. `9007199254740992.0` приводится к целому только ниже 2^53.
- Объектный вид — снимок: `from_object` клонирует значение. Меняя исходный объект `{a:"old"}` на `"new"`, JavaScript прочтёт `"new"`, здесь `"old"`.
- Возвращаемые контейнеры сравниваются по структуре, а не по тождеству: в тестах `toBe` на `value(...)` заменён равенством значений.
- `deepFreeze` не имеет аналога: `Object.freeze` делает `{a:1}` неизменяемым (запись бросает), изменяемый `Value` здесь можно сделать `{a:2}`.
  Вызовов `deepFreeze` в образце больше 27 по пакетам; все они остаются без замены в переносе.
- Тест `distinguishes_a_streaming_view_...` и срезы по 3 единицы UTF-16 в `tracks_a_write_call_...`: разрез внутри суррогатной пары
  (спецификация, строка 1086) сдвинут к ближайшему представимому месту после пары.

- `deepFreeze` — в Rust значения неизменяемы по умолчанию. Пользователи: более 27 вызовов в других пакетах dsh; аналога нет, см. «Отличия от образца».

## Вопросы ведущему
- Принять ли пару `text`/`text_utf16` (и `text_prefix`/`text_prefix_utf16`) как публичный вид? Потребителям, которым нужен `String`,
  достаточно `text`.
- Нужен ли потребителям `append` с фрагментами в UTF-16 (`&[u16]`)? Сейчас поток из `&str` не может оборвать суррогатную пару.
- В образце `README` называет `isJsonValue` проверкой «dense intrinsic arrays»; в Rust это свойство `Vec`. Если `serde_json::Value` не
  единственный носитель JSON в портируемых пакетах, нужна проверка для другого типа.
- `js_number_string`: при равноудалённых кратчайших десятичных (точное значение — кратчайшие цифры и одна `5`) берётся вариант с чётной последней цифрой, как в ECMA-262, а не округление вверх кратчайшего форматтера Rust (`1000000000000000.25` → `1000000000000000.2`); вариант проверяется обратным разбором. Фикстура `tests/fixtures/js_number_strings_ties.tsv` (26 708 строк).
