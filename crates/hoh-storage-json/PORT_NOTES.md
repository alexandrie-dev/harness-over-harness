## Отличия от образца

- Rust API использует snake_case, Arc<dyn KvUnit> и object-safe BackendFuture из hoh-storage. Config.root обязателен и без default. StorageJsonPlugin::NAME — storage-json; Deps требует Storage. Дополнительный тип ServiceKey JsonBackend предоставляет тот же Arc под именем storage.backend.json. Регистрация backend снимается до его закрытия; предоставление сервиса снимается kernel effect.
- Публичные open_single_unit/open_per_record_unit и PerRecordJsonUnit::new принимают on_close: Arc<dyn Fn() -> Result<(), BoxError> + Send + Sync>. Fallible callback передаёт исходный throw владельца без замены; закрытый unit остаётся закрытым, повторный close не вызывает callback снова. Отдельный тест обеих layouts проверяет SharedError::ptr_eq; callback самого backend возвращает Ok после освобождения open-slot.
- Вызовы методов backend/unit резервируют open-slot, проверяют closed, изменяют single-память и регистрируют write до возврата future. Собственные tokio tasks соответствуют уже начавшимся promise исходника: уронить future не означает отменить I/O. close помечает объект закрытым при вызове и ждёт уже начатые операции. Это библиотечные операции, а не фоновые context tasks; эффект плагина дожидается backend.close. Порядок конкурентных writes по-прежнему принадлежит domain, собственной очереди нет. load_all per-record не отслеживается close, как в исходнике, даже если bootstrap пишет файлы.
- JSON на диске пишется только js_json_stringify_pretty с исходным порядком полей, отступом 2 и одним завершающим LF. Чтение — js_json_parse; readFile UTF-8 использует replacement для повреждённых байтов, как Node. snapshot перечисляет integer-like record keys в порядке JS object, остальные — в порядке Map. Возвращаются клонированные Value, без JavaScript object identity. Нет undefined, циклов и исполняемого toJSON: это уже граница KvUnit в hoh-storage.
- Версии descriptor — u64 из hoh-storage. При чтении целые stamps принимаются только точно в пределах 2^53 (включительно); более высокие версии отвергаются/считаются foreign, хотя исходный JavaScript Number может их принимать. Fractional/negative stamps не совпадают с поддерживаемым descriptor. Ограничения shared JSON parser (4096 уровней, lone surrogate → U+FFFD, overflow Number → null, сообщения JSON.parse без части новых V8-суффиксов) наследуются без локального обхода.
- StorageError остаётся собственным hoh_storage::StorageError, а не HarnessError. Unknown-state хранится как StorageError и каждый раз возвращается непосредственно в BoxError: один downcast_ref::<StorageError>() узнаёт как первый отказ batch, так и все последующие отказы quarantined unit. Используется уже существующий Clone; hoh-storage не менялся. Разные boxed-клоны не сохраняют идентичность полного JS Error, но разделяют оригинальную AggregateError-причину через Arc, что отдельно проверено. Ошибка первого отказа staging/sync без ошибок restoration возвращается без замены. Дополнительный BatchDeleteError представляет исходный AggregateError и сохраняет errors в исходном порядке. У текущего StorageError стандартный source возвращает Arc<dyn Error + Send + Sync>; для downcast причины тест раскрывает этот Arc. NodeFsError представляет fs Error: code, точный текст через node_fs_error_message, исходный io::Error в source. Прочие caller errors — приватный thiserror PlainError.
- Используется именно локальный протокол src/atomic.ts. В этом пакете нет импорта @deepseek-ai/dsh-util-atomic-write; hoh-atomic-write не вызывается, поскольку его write_file_atomic не делает fsync и имеет другой протокол. Здесь сохраняются file fsync перед rename и directory fsync после него, без mkdir внутри write_atomic, retries и lock. UUID v4 формируется из getrandom. tokio File освобождает handle через Drop; отдельного сообщаемого отказа close, в отличие от Node FileHandle.close, этот API не предоставляет.
- После write_all обязательно вызывается flush до sync_all: tokio 1.54.1 только ставит write в очередь, а sync_all может поглотить его ошибку. Flush отдаёт исходный errno с syscall write; ошибка удаляет temp, сохраняет прежние байты target и откатывает single-память. В четырёх subprocess-тестах оболочка только дочернего процесса игнорирует SIGXFSZ; safe rustix setrlimit ограничивает RLIMIT_FSIZE до 64, сохраняя hard limit. После попытки записи soft limit восстанавливается. Проверяются EFBIG, точное сообщение, старые байты/snapshot, отсутствие temp и reopen. Родительский процесс и другие тесты/сборки не меняют signal/rlimit. Child-helper помечен ignored для обычного запуска и явно исполняется каждым из четырёх wrappers.
- Пути строятся общими node_path::join/dirname, readdir сортируется до обхода по именам ОС (байтам на Unix), Promise.all — join_all/try_join_all. Backup использует локальные календарные поля jiff::ZonedDateTime с исходным YYYYMMDDHHmm; не добавлены UTC или секунды. Существующий backup того же имени заменяется rename, directory fsync к backup не добавлен.
- Пустой root не становится рабочим каталогом: Rust create_dir_all("") успешно возвращает, поэтому приватный mkdir для пустого пути использует native nonrecursive mkdir, получая исходный ENOENT и сообщение через общий formatter. Регрессионный тест проверяет ровно `ENOENT: no such file or directory, mkdir ''`. Проверка обязательного root в kernel асинхронна: config-тест дожидается отказа fiber.settled(), а также проверяет ожидание storage и успешную активацию при появлении hub.
- tests/per_record_batch.rs включён как private unit-test module, чтобы hooks rename/sync оставались экземплярными и недоступными production API. autotests=false и явные integration targets json_backend/atomic_failures предотвращают повторный запуск этого файла отдельным crate. Глобального mutable состояния нет. Ожидание whole batch при close проверяется через два управляемых gate и poll(Pending), без настоящего таймера 25 мс.
- Из 40 исходных package cases 38 имеют исходные триггеры, два адаптированы из-за Value: compat-record case заменяет один throwing-toJSON отказ на I/O-отказ rename (директория в целевом пути); unmaterialized-tree case заменяет throwing-toJSON на undeclared-table отказ до mkdir. Все проверки прежних байтов, snapshot, bootstrap и retry сохранены. Эти адаптации не проверяют отказ посреди сериализации. В 18 shared contract cases используются уже согласованные hoh-storage заменители toJSON; helper не скопирован.

## Унаследованное поведение (замечания ревью 3–5)

- Durability gaps сохранены: fsync_directory синхронизирует непосредственного родителя документа, но не всю цепочку каталогов, созданных recursive mkdir; backup_record не делает directory fsync. Ошибка directory fsync после rename может означать уже заменённый target, хотя single-память откатывается. Stage batch синхронизируется до cleanup, но cleanup unlink не сопровождается ещё одним fsync; оставшийся .deleting не читается. Записи .<uuid>.tmp и *.deleting при открытии игнорируются и не удаляются — проверено на обоих layouts. Crash/power-loss atomicity batch не добавлена.
- Legacy bootstrap не является транзакцией: если record 1 опубликован, а record 2 не записался, load_all отвергается, но record 1 остаётся. При reopen созданный declared table directory подавляет bootstrap всего unit; оставшиеся записи не повторяются. Новый тест заставляет второй rename отказать из-за basename длиннее NAME_MAX, проверяет первый документ, cleanup temp, неизменённый legacy и snapshot после reopen. Failed single delete_records восстанавливает удалённые записи в порядке удаления в конце Map, а не на прежних местах; новый тест проверяет порядок snapshot и следующего опубликованного JSON.
- Legacy keys не проходят SAFE_KEY_RE: join(dir, table, key + '.json') нормализует .. и разделители, поэтому специально подготовленный ключ legacy может вывести запись за пределы unit. Это поведение источника не исправлялось; live put/delete/backup по-прежнему проверяют path-safe keys.
- Stamps остаются числами JavaScript при чтении/записи общими js_json_*: около 2^53 разные целые литералы могут округляться к одному Number. Текущее ограничение natural на точно представимые целые до 2^53 включительно сохранено; stamps выше предела отказываются/считаются foreign, в отличие от источника, который может принять такой Number. Ни запрета в descriptor, ни нового формата stamp в этом круге не добавлено.

## Не перенесено

Не пропущен ни один исходный package case: 40/40 развёрнутых сценариев, с двумя указанными адаптациями. JavaScript toJSON execution/throw непредставимы в Value; их точный триггер и rollback после serialization failure не воспроизведены. npm exports/types как механизм не переносится по PORTING §8.

Отдельный отказ Node FileHandle.close не воспроизведён: tokio File закрывает handle через Drop без возвращаемого Result. Нормальное закрытие и предварительный fsync реализованы; этот редкий error path остаётся указанным ограничением.

## Не проверено

- Windows-ветка fsync_directory возвращает сразу, как исходник; Windows и macOS не запускались. Linux-тесты проверяют байты, private permissions, реальный rename rollback, очистку temp, reopen, source cases и управляемые staging/sync/restore отказы. Настоящее отключение питания/crash durability и ошибки закрытия дескриптора не моделировались.
- Случайные UUID и локальное текущее время backup проверены по структуре/поведению, а не по заранее фиксированным значениям.
- Реальным ограничением файла воспроизводится EFBIG; ENOSPC, EDQUOT и EIO отдельно не инъецировались. Сигнал и лимит меняются только в isolated child, не в основном тестовом процессе.
- Path helper реализует только path.posix; Node на Windows использует path.win32. Системные именованные errno в hoh-error реализованы для Unix; на не-Unix helper сохраняет fallback Display. Поэтому Windows-написание возвращаемого backup path и системных сообщений не заявлено совпадающим.

## Вопросы ведущему

В hoh-storage недостающих API нет. Для точного поведения Windows нужны общие path.win32 join/dirname и Windows mapping системных кодов/текстов в hoh-util-workspace-path/hoh-error; их текущие API предоставляют POSIX/Unix. Эти чужие crates не менялись. Также у tokio File нет async close с Result: отдельный отказ Node close не воспроизведён. Других вопросов нет.
