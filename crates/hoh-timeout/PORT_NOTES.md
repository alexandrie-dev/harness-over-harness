## Отличия от образца
- `clamp_timeout` принимает Option для hint и имени (None означает timeoutMs). Исключения представлены Result с публичным enum TimeoutError; TimeoutReason реализует Error/Display, имя класса — имя Rust-типа.
- Миллисекунды — f64, поскольку источник принимает дробные задержки. Планирование повторяет setTimeout: отбрасывает дробь и использует минимум 1 ms; reason сохраняет исходное значение. MAX_TIMER_DELAY_MS — u64.
- `timeout_of` принимает саму причину (Option<&dyn Any + Send + Sync>), а не signal или объект-носитель { reason }, как timeoutOf образца. Вызывающий извлекает reason самостоятельно; в сигнатуре нет типов runtime.
- Публичный AbortSignal — временная замена AbortSignal/AbortController: new/default, clone, abort, aborted, reason, cancelled. reason хранится как Arc<dyn Any + Send + Sync>; первая причина сохраняется вместе с идентичностью Arc. Fusion синхронно передаёт отмену; уведомления ожидателей используют tokio::sync::watch. Связи с получателями слабые, глобального реестра нет.
- Deadline и IdleWatchdog используют tokio::time и управляемые JoinHandle. Deadline отменяет таймер на Drop; в образце таймер продолжает работать до явного dispose или срабатывания. Нужен активный Tokio runtime для положительной задержки.
- IdleWatchdog::next принимает Future одного запроса итератора вместо AsyncIterator. Future и результат должны быть Send + 'static, потому что запрос исполняется в задаче Tokio. Проверка concurrent demand и запуск таймера происходят при вызове, до polling результата. Завершение demand снимает таймер даже если результат ещё не прочитан, как у eager Promise. dispose/Drop watchdog снимают таймер, но не завершают outstanding next; закрытие watch-канала не считается таймаутом.
- По решению ведущего после ревью, при собственном таймауте demand уничтожается (Drop), а не продолжает выполняться, как проигравший Promise.race в образце. Задача next принадлежит возвращённому future; его Drop отменяет задачу и уничтожает demand, поэтому после удаления watchdog и его futures фонового запроса не остаётся. Отдельной detached-задачи demand нет.
- Публичный IdleWatchdogError различает Timeout(Arc<TimeoutReason>), State(TimeoutError), Task(tokio::task::JoinError). Последний вариант представляет только Rust-специфичные сбой задачи/остановку runtime. Результат demand не преобразуется и может быть Result.
- Пункт ревью о фиксированном тексте `Aborted` проверен: в текущем API этого варианта/типа нет, а `cancelled()` возвращает исходный Arc причины. Адаптер с фиксированным текстом `Aborted` отличался бы от повторного выбрасывания собственной причины signal в образце; такое поведение текущему crate не приписывается.

## Вопросы ведущему
- Согласовать AbortSignal и носитель причины с типом отмены ядра, когда будет написан docs/kernel.md.
- Согласовать Deadline/IdleWatchdog: tokio::time::sleep_until, tokio::spawn, JoinHandle::abort, watch-уведомления и dispose/Drop с будущим владением таймерами ядра.
- Согласовать API next(Future + Send + 'static), владение задачей eager-исполнения, вариант ошибки JoinError и согласованное ведущим уничтожение demand при timeout/Drop future с будущим API потоков ядра. dispose watchdog снимает таймер, но не отменяет outstanding demand, как источник.
- Уточнить место упомянутого в ревью адаптера `Aborted`: в текущем hoh-timeout его нет; фиксированный текст вместо исходной причины не заявлен как реализованное отличие.
- В исходнике next после первого собственного timeout слушает только новое событие abort: уже отменённый watchdog второй раз не отклоняет demand таймером. Это поведение сохранено, не исправлялось.
