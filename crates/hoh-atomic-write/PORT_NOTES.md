## Отличия от образца
- Async I/O через tokio; mode/dir_mode — u32, wait_ms — u64. with_file_lock и его operation возвращают Result<T, hoh_error::BoxError>: IO и произвольные ошибки операции передаются без обёртки. Временный enum AtomicWriteError удалён: ошибки отмены теперь имеют общий тип hoh_timeout::AbortError или представляют исходный SharedError причины.
- По решению ведущего PORTING.md §7 FileLockError — пустая структура с NAME и new(PathBuf), возвращающим конкретный HarnessError::named. Дополнительный FileLockErrorCode::FileLockTimeout.as_str() задаёт FILE_LOCK_TIMEOUT; FileLockErrorDetails { lock_path: PathBuf } прикрепляется через with_detail и читается detail::<FileLockErrorDetails>(). name/code/message совпадают с образцом. За BoxError таймаут распознаётся напрямую через HarnessError::of; CodedError, Deref и обёртки ошибок удалены. Протокол записи/takeover/retry при этой адаптации не менялся.
- FileLockOptions.signal — Option<hoh_timeout::AbortSignal>. Оба throwIfAborted (до acquisition и перед operation) выбрасывают сам SharedError причины с сохранением ptr_eq. Abortable wait, как node:timers/promises, возвращает новый общий AbortError с точным текстом "The operation was aborted" и cause = исходный SharedError; он узнаётся через is_abort_error. После входа cancellation принадлежит операции. Дополнительный AbortError::with_cause введён в hoh-timeout именно для этого контракта.
- По решению ведущего fix3 приватный FileGuard существует до первого await, создающего файл. Отдельные guards владеют `<file>.lock`, `.lock.takeover-<hash>` и случайным `.tmp`: lock защищён от начала acquisition через operation до удаления; claim — от создания до окончания takeover/удаления claim; temp — от создания через rename или error cleanup. При нормальном успехе guard снимается после удаления lock/claim либо после rename temp. Drop незавершённого future удаляет созданный им файл best-effort, не трогая существующий чужой файл при неудачном exclusive create.
- Создание/write_all/flush выполняются одним spawn_blocking worker. Общая ownership-state доступна guard и worker: исходный File (через Arc, без второго open) и metadata регистрируются сразу после успешного exclusive open. Если future уже dropped, worker удаляет даже пустой поздно созданный файл до записи; при отмене во время записи cleanup выполняется в Drop и повторяется при завершении worker. На Unix fd сохраняет inode, dev/ino не позволяют удалить подменённый inode. При недоступной metadata guard не отключается: освобождает свой fd и сравнивает запись с написанной (для незавершённой записи — её префикс), затем удаляет файл. Для подтверждённого Unix inode незавершённый/temp файл удаляется без чтения содержимого; для завершённого lock/claim проверяется запись держателя.
- Конструктор FileGuard теперь выполняет только выделение состояния/копирование данных; файловых вызовов в нём нет. Open, metadata, write и flush находятся на blocking worker. Деструктор выполняет blocking metadata/read/unlink/close на том потоке, который уничтожает future (обычно async-поток). Обычный unlink в Runtime.remove тоже выполняется синхронно в текущем poll: отложенное удаление не должно пережить освобождение claim и удалить файл следующего держателя. Эти небольшие по назначению операции приняты как необходимая цена cancel-safety и невозможности await в Drop; их длительность зависит от FS. Большая запись/flush не выполняется на async-потоке.
- Тесты Fake приостанавливают write_new после создания lock/claim/temp и remove в takeover/error cleanup; Drop удаляет owned-файл, следующий writer/takeover проходит немедленно. Есть тесты поздно завершающегося worker, пустой записи, отказа identity, подмены record/inode и timeout вокруг уже начатой operation.
- Abortable wait использует biased select с abort первым: при готовых сигнале и таймере выигрывает AbortError с исходной причиной; проверено под paused time.
- transient на Unix принимает ровно raw EACCES, EBUSY, EPERM (rustix Errno::ACCESS/BUSY/PERM); ErrorKind без raw code не подходит. На Windows явно сопоставлены Win32 5 (access denied), 1314 (privilege not held), 32/33 (sharing/lock violation), 170 (busy); широкие проверки PermissionDenied/ResourceBusy удалены. Windows mapping не запускался на Windows, дополнительный cfg(windows) тест готов.
- Тестовые filesystem/probe hooks приватны; tests/atomic-write.rs подключается модулем unit tests, autotests=false исключает повторную компиляцию файла как integration crate. Тесты таймеров работают с paused tokio clock. Параметризованные записи/платформы сохранены циклами.
- Дополнительное поле FileLockOptions::process_exited позволяет владельцу переопределить проверку PID (true только при ESRCH). По умолчанию на Unix используется безопасный rustix::process::test_kill_process: успех означает живой процесс, ESRCH — завершившийся, EPERM — живой процесс другого пользователя; все остальные ошибки, как в образце, не доказывают завершение (false). Протокол повторно читает record и проверяет PID под hash-claim. На Windows default probe возвращает прежний Unsupported до этапа 5.

## Не перенесено
Нативный Windows signal-zero probe — ждёт этапа 5 по решению ведущего; до этого без переопределения process_exited возвращается Unsupported. Реальный exited-process тест включён на Unix (cfg(unix)); как и в образце, на Windows он не запускается из-за быстрого переиспользования PID. Каталога locale нет.

## Не проверено
Windows/macOS runtime не запускались. Windows retry/EPERM проверены инъекцией raw Unix errno на Linux, не реальными Win32 sharing violations. Реальный Unix probe проверен на завершившемся процессе, живом родителе и PID 1 под non-root; при отсутствии видимого parent (PID 1/другой namespace) либо root для PID 1 тест печатает причину пропуска. Отрицательные raw errno тесты включают EIO, ENOENT, EAGAIN, EEXIST, ENOTEMPTY. Drop cleanup best-effort: при отказе FS в metadata/read/unlink гарантировать освобождение нельзя; начатый blocking worker может закончить I/O после Drop, но получает cancellation и выполняет cleanup. На Windows guard проверяет содержимое, без Unix-проверки inode; share-delete/rename с удерживаемым creating handle отдельно на Windows не проверены.
