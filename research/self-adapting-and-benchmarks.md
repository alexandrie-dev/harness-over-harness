# Самоадаптирующиеся harness'ы и бенчмарки адаптации

Обзор для продукта с рабочим названием Harness Over Harness. Дата: 2026-11-16.

**Как читать.** Факты взяты из источников, открытых в этой сессии: полные тексты arXiv, официальная документация, README склонированных репозиториев. Без пометки — проверено по первоисточнику. **[В]** — известно только по вторичному источнику (блог, агрегатор, выдача поиска). **[Н]** — не проверено или по памяти. **[мой вывод]** — моя интерпретация, а не утверждение авторов. Раздел 5 собирает всё непроверенное. Ничего из чужого кода не запускалось.

## 0. Что меняет наш дизайн

Ссылки на источники каждой цифры — в разделах 1–3.

1. **Harness² существует и почти совпадает с идеей «harness поверх harness».** Это работа Google Cloud AI Research (октябрь 2026): надстройка над штатными OpenCode и Codex, которая под каждую задачу правит восемь файловых компонентов harness'а и копит библиотеку удачных наборов. Код открыт под Apache 2.0. Его надо прочитать до проектирования своего ядра. Наше отличие уже: пользователь сам называет повторяющуюся задачу, плагин живёт долго, исполнитель — локальная модель.
2. **Умения, написанные моделью «из головы», вредят.** В SkillsBench самогенерируемые skills дали от −8,1 до −11,5 п.п. к запуску без skills; в исследовании AGENTS.md сгенерированные файлы не подняли успех и удорожили запуск на 20–23%. Работает только то, что выведено из трасс реальных прогонов и прошло проверку на отложенных экземплярах.
3. **Готовый «человеческий» skill может ухудшить слабую модель.** Официальный xlsx-skill Anthropic опустил Qwen3.5-35B на SpreadsheetBench-Verified с 19,0 до 9,67, а тот же skill, доработанный по трассам прогонов, дал 22–37. Рельсы надо подгонять под конкретного исполнителя.
4. **Выигрыш живёт в скриптах, инструментах и middleware, а не в прозе.** У AHE замена одного системного промпта дала −2,3 п.п.; у Harness² удаление скриптов стоило 7,4 пункта на офисных задачах; в EvoClawBench текстовые skills ни разу не окупились по токенам; Compiled AI окупается примерно к 17-му запуску. Плагин задачи должен уметь превращать устоявшиеся шаги в код.
5. **Регрессии почти не предсказываются.** Редактор AHE угадывает будущие исправления в 5 раз лучше случайного, а будущие поломки — только в 2 раза. Значит, каждое обновление плагина должно проходить повтор всех ранее принятых экземпляров.
6. **Бенчмарк без равного бюджета и без нетронутого тестового набора завышает результат.** Работа «Rethinking the Evaluation of Harness Evolution» показала: на Terminal-Bench 2.1 эволюция harness'а не обгоняет простое «несколько попыток» при равном бюджете, а на отложенных задачах даёт +1,2 / 0 / −1,4 пункта. «Held-out» в Self-Harness участвует в отборе правок, то есть не является тестом.
7. **Явное объявление задачи пользователем — наше преимущество.** При росте библиотеки с 5 до 100 skills точность фактического использования (actual-use precision) падает с 29,6% до 3,3% ([arXiv 2608.14036](https://arxiv.org/abs/2608.14036), по аннотации). Если пользователь сам говорит «это та же задача», проблема поиска нужного плагина исчезает.

### 1.3 Agent Skills в четырёх harness'ах

Формат задан открытой спецификацией [agentskills.io](https://agentskills.io/specification): каталог с `SKILL.md` (обязательные `name` до 64 символов и `description` до 1024), необязательные `scripts/`, `references/`, `assets/`. Загрузка трёхступенчатая: около 100 токенов метаданных на каждый skill при старте, тело до 5000 токенов при активации, остальные файлы по требованию.

| Harness | Где лежат skills | Вызов | Что есть сверх формата |
|---|---|---|---|
| Claude Code ([docs](https://code.claude.com/docs/en/skills)) | `.claude/skills`, `~/.claude/skills` | Модель сама или `/имя` | Запуск в субагенте (`context: fork`), запрет автозапуска, выбор модели. Плагин skill-creator гоняет набор запросов с skill'ом и без него и пишет `benchmark.json` с долей успеха, временем и токенами; `claude plugin eval` делает то же для плагина и возвращает ненулевой код ниже порога |
| Codex ([docs](https://learn.chatgpt.com/docs/build-skills)) | `.agents/skills` в проекте и `$HOME`, `/etc/codex/skills` | Неявно по описанию или явно через `$` | Встроенные `skill-creator` и `skill-installer`; черновик skill'а из записанного workflow |
| OpenCode ([docs](https://opencode.ai/docs/skills/)) | `.opencode/skills`, а также `.claude/skills` и `.agents/skills` | Инструмент `skill` по идентификатору | Права `allow`/`ask`/`deny` на каждый skill, в том числе по агентам |
| Qwen Code ([docs](https://qwenlm.github.io/qwen-code-docs/en/users/features/skills/)) | `.qwen/skills`, `~/.qwen/skills`, также `.agents/skills` | Модель сама или `/имя` | `/learn` превращает URL, каталог, текст или видео в skill с пометкой `source: learned`. Auto Skill сам создаёт `auto-skill-*`, через 30 дней без успешного использования помечает устаревшим, через 90 архивирует; `/curator` управляет этим |

Следствие: один и тот же каталог плагина в `.agents/skills` прочитают Codex, OpenCode и Qwen Code. Часть «каждая задача — плагин» уже реализована внутри Qwen Code (`/learn`, Auto Skill), а DeepSeek Harness позволяет создавать плагины в чате в «Creator mode» ([страница продукта](https://deepseek.com/en/harness/): «everything is a plugin», основа Cordis, MIT, публичный preview). Ни один из этих механизмов по документации не проверяет созданный skill на отложенных экземплярах задачи.

Безопасность: по [arXiv 2601.10338](https://arxiv.org/abs/2601.10338) в 26,1% из 31 132 skills найдена хотя бы одна уязвимость; по [2602.06547](https://arxiv.org/abs/2602.06547) подтверждено 157 вредоносных skills [В, обе цифры]. Скрипты в плагине — исполняемый код с правами пользователя.

### 1.4 Файлы памяти

Claude Code загружает CLAUDE.md и автопамять в каждую сессию и прямо называет их «context, not enforced configuration»; рекомендация — до 200 строк на файл, автопамять читается в пределах первых 200 строк или 25 КБ ([docs](https://code.claude.com/docs/en/memory)). Codex использует AGENTS.md, Qwen Code — QWEN.md или AGENTS.md в зависимости от версии [В].

Единственная найденная контролируемая проверка — [arXiv 2602.11988](https://arxiv.org/abs/2602.11988) (четыре агента, включая Qwen Code с локальным Qwen3-30b-coder):

- сгенерированные моделью файлы снизили долю решённых задач в 5 из 8 постановок, в среднем на 0,5% и 2% (незначимо), и подняли стоимость на 20% и 23%;
- файлы, написанные разработчиками, дали +2,4% (p=21%), но значимо лучше сгенерированных;
- инструкции из файлов агенты выполняют, а обзоры репозитория не сокращают путь к нужным файлам.

Вывод для базовой линии «harness с обычным memory-файлом»: это честный, но слабый соперник; его надо строить так же добросовестно, как плагин, иначе сравнение ничего не скажет.

### 1.6 Критика самой постановки

[«Rethinking the Evaluation of Harness Evolution for Agents»](https://arxiv.org/abs/2607.12227) (июль 2026, Allen Institute for AI и соавторы) сравнивает при равном бюджете четыре способа потратить вычисления: параллельные попытки, последовательную доработку, эволюцию harness'а на наборе задач, доработку harness'а под один экземпляр. Результаты на Terminal-Bench 2.1 с Opus 4.6, GPT-5.4 и GPT-5.4 mini:

- эволюция harness'а не обгоняет простые повторные попытки ни с тестами, ни без них;
- при разбиении 45 / 10 / 34 (обучение, валидация, тест) эволюционировавший harness даёт на тесте +1,2, 0 и −1,4 пункта, в среднем ноль;
- при удвоении бюджета вывод не меняется: самогенерируемая обратная связь слишком шумна.

Где эволюция всё же помогает: длинные игры с частой и точной обратной связью (ARC-AGI-3: +80% к базовой линии поиска, EdgeBench: +11%). [мой вывод] Наш случай ближе ко второму: экземпляры одной семьи задач сильно похожи, и адаптация идёт под семью, а не под «программирование вообще». Но доказывать это придётся тем же способом: равный бюджет и нетронутый тест.

## 2. Наш механизм: ближайшие аналоги и что известно

Механизм: пользователь называет повторяющуюся задачу → система готовит плагин задачи (инструкции, инструменты или скрипты, источники, память, проверки) → следующие экземпляры идут быстрее и надёжнее, в том числе на слабой локальной модели.

### 2.1 Ближайшие аналоги

| Работа | В чём совпадает | В чём расходится |
|---|---|---|
| **Harness²** | Надстройка над готовыми harness'ами; те же составные части плагина (skills, скрипты, память, guardrails, middleware); сильный редактор и слабый исполнитель; офисные задачи | Адаптация под каждую отдельную задачу на лету, а не под объявленную семью; нет проверок по эталону; каждая задача оплачивает лишние прогоны |
| **Trace2Skill** | Skill для класса задач выводится из трасс и проверяется на отложенных; локальные Qwen 35B и 122B; таблицы | Только текстовый skill; сигнал успеха берётся из бенчмарка |
| **LATM** | «Сильная делает инструмент, слабая пользуется», диспетчер по классам задач, амортизация разовой стоимости | Узкие алгоритмические задачи 2023 года |
| **Compiled AI** ([arXiv 2604.05150](https://arxiv.org/abs/2604.05150)) | Разовая генерация, затем детерминированное исполнение; обработка счетов (DocILE); формула окупаемости | На входе формальная YAML-спецификация, а не слова пользователя |
| **AutoScraper** ([arXiv 2404.12753](https://arxiv.org/abs/2404.12753)) | Ровно задача «разбор сайта»: модель один раз пишет скрейпер под сайт, дальше работает он; метрика «исполнимость на многих страницах сайта» | Только извлечение полей из HTML |
| **SkillLearnBench** ([arXiv 2604.20087](https://arxiv.org/abs/2604.20087)) | Skill создаётся один раз на задачу и проверяется на нескольких экземплярах с другими параметрами | Это бенчмарк, а не система |
| **Qwen Code `/learn` и Auto Skill**, **Claude skill-creator** | Тот же пользовательский жест: «запомни, как это делать» | Нет отложенной проверки, нет компиляции в код, работает внутри одного harness'а |

### 2.2 Сильная модель пишет рельсы, слабая по ним идёт

Что подтверждено измерениями:

- **Перенос от сильной к слабой работает.** Harness, доработанный редактором Opus 4.8 для Gemini 3.5 Flash, без изменений поднял GLM-5 на 17,3 пункта (58,5 → 75,8) на WorkBuddy-Bench Code ([Harness²](https://arxiv.org/abs/2610.14224), прил. E.3). Harness, эволюционировавший на GPT-5.4, дал +5,1…+10,1 п.п. более слабым моделям других семейств ([AHE](https://arxiv.org/abs/2604.25850)). В [SkillsBench](https://arxiv.org/abs/2602.12670) MiniMax M2.7 со skills (34,9%) обходит более сильные конфигурации без них (32,7% и 29,7%).
- **Слабая модель выигрывает больше сильной.** В Harness² GLM-5 получает больший абсолютный прирост, чем Gemini 3.5 Flash; в AHE прирост у «дальних от насыщения» моделей больше; в Self-Harness Qwen3.5-35B удваивает результат.
- **Сильный редактор не обязателен, обязательны трассы.** В Harness² все пять моделей улучшаются, когда редактор и исполнитель совпадают (GLM-5: +13,7 на LAB). Self-Harness и Trace2Skill обходятся одной 35B-моделью. Общий знаменатель успешных случаев — разбор реальных прогонов и отбор по результату, а не сила автора.
- **Одно и то же правило по-разному действует на разные модели.** [MASA](https://arxiv.org/abs/2605.30723): skill, полезный одной модели, может вредить другой; Trace2Skill показывает это на xlsx-skill'е. [AFTER](https://arxiv.org/abs/2606.23127): skills, выведенные из трасс нескольких моделей, дают 73,1% при переносе и обходят любой одномодельный источник.
- **Автор без трасс не помогает даже если он сильный.** SkillsBench: skills от Opus 4.7, GPT-5.5 и Gemini 3.1 Pro, написанные до решения задачи, дали −8,1, −11,3 и −11,5 п.п. Разбор причин: в 10 из 12 проверенных трасс исполнитель вообще не открыл созданные skills; использованные skills закрепляли уверенные ошибки (жёстко зашитый пересчёт единиц в 1000 раз); единственный яркий выигрыш оказался утечкой ответа в skill. [SkillLearnBench](https://arxiv.org/abs/2604.20087): лучший метод закрывает около 45% разрыва до человеческих skills; итерации помогают только с внешней обратной связью, самооценка ведёт к «рекурсивному дрейфу»; более сильная модель не даёт лучших skills.
- **Абстракция теряет полезное.** [SkillEvolBench](https://arxiv.org/abs/2605.24117): сырые трассы часто работают лучше выжатых из них skills; лишние обновления дают «эпизодный дрейф и процедурный мусор». Meta-Harness: сводки вместо трасс обнуляют поиск. Вывод: вместе с плагином надо хранить исходные трассы и принятые экземпляры.

### 2.3 Проверка сгенерированных инструментов

Приёмы, которые встречаются в работах с положительным результатом:

| Приём | Где | Что даёт |
|---|---|---|
| Отложенные экземпляры, скрытые от автора | Trace2Skill, Meta-Harness, HEXIS | Отделяет процедуру от запоминания ответа |
| Повтор всех ранее принятых трасс перед принятием правки | [HEXIS](https://arxiv.org/abs/2609.30123): статические проверки и replay | Ловит регрессии, которые автор не предвидит |
| Ворота «не хуже на реальном прогоне» | Self-Harness, [SkillGLoW](https://arxiv.org/abs/2609.02217) | Запрет размена одного набора на другой |
| Манифест правки с прогнозом и откатом по файлу | AHE | Аудит и дешёвый откат |
| Четыре стадии: безопасность (Bandit, Semgrep), синтаксис и типы, исполнение в песочнице на фикстурах, точность против эталонных данных | [Compiled AI](https://arxiv.org/abs/2604.05150) | Код до развёртывания проходит обычный инженерный контроль |
| Отдельный критик, а не автор | Voyager, Ouroboros | Без критика −73% у Voyager |
| Отказ компилировать при недоопределённом необратимом действии; эскалация вместо действия на ненаблюдавшейся ветке | [TraceCompiler](https://arxiv.org/abs/2608.02680) | Безопасное поведение на новом случае |
| Аудит плагина на строки конкретного экземпляра: имена файлов, пути, «магические числа», ожидаемые ответы | SkillsBench, Meta-Harness | Ловит утечку ответа в плагин |
| Хеш плагина до и после прогона | [EvoClawBench](https://arxiv.org/abs/2607.09711) | Прогон «с плагином» не превращается в новое авторство |
| Скрытие проверяющих функций от того, кто правит | DGM | Иначе система оптимизирует метрику, а не задачу |

Открытое место: все эти приёмы требуют сигнала корректности. Harness² обходится без него, но платит несколькими прогонами на задачу и признаёт, что контрасты не проверяют правильность.

### 2.4 Когда компилировать в детерминированный код

Общая рамка Anthropic: workflow — «predefined code paths», агент сам управляет процессом; усложнять только когда простое решение не справляется ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)). Измерения 2026 года уточняют:

- **Текстовые skills экономят шаги, но не токены.** EvoClawBench: у полной цепочки «написать skill и применить» коэффициент токен-эффективности к прямому запуску 0,30–0,40, то есть токенов уходит примерно в 2,5–3,3 раза больше (пересчёт мой); по токенам и деньгам окупаемости нет, по времени — после 9–14 повторов. При этом исход неустойчив: DeepSeek-V4-Pro упал с 77,77% до 4,80% и 0,99%.
- **Код окупается быстро.** Compiled AI: разовая генерация 9600 токенов, окупаемость к 17-й транзакции, в 57 раз меньше токенов на 1000 транзакций; на счетах DocILE вариант с ограниченными вызовами LLM внутри кода сравнялся с прямым LLM по извлечению полей (80,0%) и дал лучший результат по строкам (80,4%). HEXIS: skill, скомпилированный в конечный автомат, даёт +16,2 п.п. к «skill + ReAct», а Qwen3.8-27B тратит на 38,4–88,9% меньше токенов. [SkillCraft](https://arxiv.org/abs/2603.00718): до −80% токенов при сохранении и повторном использовании составных инструментов. [Agentic Plan Caching](https://arxiv.org/abs/2506.14852): −50,31% стоимости и −27,28% задержки.
- **В офисных задачах главную роль играют скрипты.** Harness², абляция на WorkBuddy-Bench: без skills −3,6 на Code и −6,9 на Web; без скриптов −7,4 на Office.
- **Компилятор должен уметь отказаться.** TraceCompiler свёл 34 вызова API к 11, но прошёл 15 из 21 теста: провальные случаи требовали ветки, которой не было в трассах, и система эскалировала вместо действия.

Правило, которое из этого следует [мой вывод]:

| Шаг | Форма в плагине |
|---|---|
| Одинаков во всех принятых трассах, вход и выход типизированы (скачать страницы, разобрать таблицу, собрать файл по шаблону) | Скрипт, без модели |
| Требует понимания текста, но имеет фиксированную схему результата (извлечь поля из письма, классифицировать документ) | Ограниченный вызов модели внутри скрипта со схемой вывода и проверкой |
| Различается между экземплярами или встречался один раз | Остаётся агентным, с инструкцией и проверкой результата |
| Необратимое действие с неясными условиями | Не компилируется; подтверждение человеком |

Компилировать имеет смысл после того, как есть несколько успешных трасс одной семьи: по одной трассе нельзя отличить постоянное от случайного. Точное число не установлено ни в одной из работ.

### 2.5 Что из этого следует для плагина задачи

1. Плагин создаётся из трасс: первый экземпляр решается «в холодную» с записью, плагин выводится после, а не до.
2. При объявлении задачи нужен источник истины: 2–3 пары «вход → ожидаемый результат» от пользователя или подтверждение им первого результата. Без этого остаётся только схема Harness² с её ценой.
3. В плагине хранятся: инструкция (коротко: в SkillsBench компактные skills дают +19,0…+21,5 п.п., исчерпывающая документация +0,7), скрипты, проверки результата, список источников, память фактов, принятые экземпляры с трассами.
4. Обновление плагина принимается только после повтора всех принятых экземпляров.
5. Плагин привязан к модели-исполнителю: при смене модели нужна повторная проверка, а не перенос «как есть».
6. Плагин выбирается по явному объявлению пользователя, а не поиском по описанию.
7. Скрипты плагина исполняются в песочнице и проходят статический анализ.

Полезный результат: память из неверных собственных ответов ухудшает итог, иногда ниже запуска без памяти |
| **LifelongAgentBench** ([2505.11942](https://arxiv.org/abs/2505.11942)) | Три среды (БД, ОС, граф знаний), задачи связаны через таксономию атомарных навыков (22 SQL, 29 Bash) | Успех с повтором опыта и без | Автоматическая проверка результата (состояние БД, хеши файлов); новый контейнер на задачу | Низкая. Результат: больше прошлого опыта в контексте может ухудшать |

| **Terminal-Bench 2.1 в «Rethinking…»** ([2607.12227](https://arxiv.org/abs/2607.12227)) | 45 / 10 / 34 и сравнение с параллельными и последовательными попытками при равном бюджете K=5 | pass@1, pass@5 | Тест не участвует ни в поиске, ни в отборе; равный бюджет обратной связи и вычислений | Нет |

Что повторяется от работы к работе:

- Прирост есть там, где экземпляры структурно похожи (Evo-Memory, SkillLearnBench, CL-Bench), и исчезает или становится отрицательным на открытых задачах.
- Парное сравнение на одном и том же экземпляре (с адаптацией и без) — общий стандарт: SkillsBench, CL-Bench, PAST-Bench.
- Самые информативные добавки последних месяцев: полная стоимость цепочки (EvoClawBench), доказательство того, что артефакт действительно использовался (PAST-Bench, аудит SkillsBench), задачи-ловушки (SkillEvolBench), равный бюджет (Rethinking).
- Офисные задачи с детерминированной проверкой редки. Чаще оценка смешанная: правила плюс LLM-судья (WorkBuddy Office, JobBench, LAB), а это добавляет шум, сравнимый с эффектом.
- Ни один найденный бенчмарк не измеряет вмешательства человека и не сравнивает локальную модель с фронтирной в роли исполнителя заранее подготовленных рельсов.

## 4. Кандидаты нашего бенчмарка

### 4.1 Общая рамка

**Семья задач** — повторяющийся тип работы с генератором экземпляров и проверкой результата. Примеры: «извлечь поля из счетов такого вида в таблицу», «собрать каталог товаров с сайта в CSV», «заполнить форму по набору документов», «свести две выгрузки».

**Экземпляры каждой семьи делятся на четыре непересекающихся набора:**

| Набор | Кто видит | Зачем |
|---|---|---|
| D_adapt (3–5) | Система при создании плагина | Материал адаптации |
| D_val (3–5) | Собственные ворота плагина | Отбор правок |
| D_test (8–10) | Никто до заморозки плагина | Итоговые «тёплые» прогоны |
| D_shift (4–5) | Никто до заморозки | Контролируемый сдвиг: новая вёрстка сайта, другой шаблон документа, изменённая схема |

Три набора вместо двух закрывают ошибку Self-Harness, где «отложенный» набор участвует в отборе.

**Фазы:** холодный прогон на D_test без плагина → адаптация на D_adapt и D_val с учётом всех затрат → заморозка плагина с хешем → тёплые прогоны на D_test и D_shift в чистых рабочих каталогах.

**Метрики:**

| Метрика | Определение |
|---|---|
| Успех s | Доля экземпляров, прошедших проверку; минимум 3 попытки на экземпляр; отдельно — доля экземпляров, прошедших все попытки (надёжность) |
| Время | Медиана и 90-й перцентиль от запроса до результата |
| Токены и вызовы | Вход, выход, кэш; число вызовов модели и инструментов; доля ошибочных вызовов инструментов |
| Вмешательства человека | Число вопросов, подтверждений и исправлений на экземпляр и отдельно за адаптацию; считается по симулированному пользователю со списком известных ему фактов |
| Стоимость адаптации A | Токены, время, вмешательства и расход сильной модели на создание плагина |
| Амортизированная стоимость | (A + N·C_тёпл) / N для N = 5, 20, 100 |
| Точка окупаемости | N* = A / (C_хол − C_тёпл), отдельно по токенам, времени и деньгам; «не достигается», если C_тёпл ≥ C_хол (формула из Compiled AI) |
| Стоимость успешного результата | C / s для холодного и тёплого режимов; окупаемость по этой величине учитывает и надёжность |
| Прирост | g = s_тёпл − s_хол; нормированный ĝ = g / (1 − s_хол) |
| Регрессии | Доля экземпляров, которые проходили холодными и не проходят тёплыми |
| Интерференция | Успех по семье A после установки плагинов B, C, … |
| Сдвиг | Успех на D_shift и доля случаев, когда плагин сам обнаружил несоответствие и эскалировал, а не выдал неверный результат |
| Использование | Доля тёплых прогонов, где плагин был загружен и его скрипты исполнялись |
| Закрытый разрыв | (s_наш − s_хол) / (s_человеческий плагин − s_хол) на 2–3 семьях с плагином, написанным вручную |

**Базовые линии:**

| Код | Условие | Зачем |
|---|---|---|
| B0 | Голый внутренний harness | Холодная точка |
| B1 | Внутренний harness с обычным memory-файлом, который он сам пишет на тех же D_adapt при том же бюджете | Соперник из задания |
| B2 | Родной механизм harness'а: `/learn` и Auto Skill в Qwen Code, skill-creator в Claude Code | Показывает, что даёт надстройка сверх уже встроенного |
| B3 | Голый harness с бюджетом повторных попыток, равным амортизированной стоимости адаптации | Контроль равного бюджета |
| B4 | Плагин, написанный человеком | Верхняя граница |
| H | Наш harness | Измеряемая система |

**Модели.** Исполнитель: локальный Qwen на DGX Spark и фронтирная модель. Автор плагина: та же локальная модель или фронтирная. Ключевые клетки: «автор локальный, исполнитель локальный» (данные не покидают площадку) и «автор фронтирный, исполнитель локальный». По сообщениям на форуме NVIDIA, Qwen3.5-35B-A3B даёт на Spark порядка 50–115 ток/с, Qwen3.5-122B-A10B — 40–51 ток/с ([тред 1](https://forums.developer.nvidia.com/t/custom-built-vllm-qwen3-5-35b-on-nvidia-dgx-spark-gb10-sustained-50-tok-s-1m-context/362590), [тред 2](https://forums.developer.nvidia.com/t/qwen3-5-122b-a10b-on-single-spark-up-to-51-tok-s-v2-1-patches-quick-start-benchmark/365639)) [В]; какая модель стоит у заказчика, неизвестно.

**Защита от утечек и подгонки:**

- D_test и D_shift хранятся вне рабочего каталога адаптации; в каталоге адаптации нет верификаторов и ожидаемых результатов.
- Плагин хешируется при заморозке и после каждого тёплого прогона.
- Автоматический аудит плагина на строки конкретных экземпляров.
- Сайты — только замороженные локальные снимки; сеть в прогонах закрыта.
- Часть семей закрыта от разработчиков harness'а: на открытых семьях ведётся разработка, на закрытых публикуется результат.
- Экземпляры порождаются генератором с параметрами, а не берутся готовыми из публичных наборов: это даёт неограниченный запас отложенных экземпляров и снимает вопрос о попадании в обучающие данные.
- Проверки детерминированные; LLM-судья допускается только как отдельная, явно помеченная часть оценки.
- Доверительные интервалы по попыткам и по экземплярам; порядок семей перемешивается.

### 4.2 Кандидат A: парные семьи

6–8 семей, все условия B0–B4 и H, одна адаптация на семью, результат — таблица «семья × условие × модель». По устройству это SkillLearnBench с добавленными D_val, D_shift, стоимостью адаптации и контролем равного бюджета.

| | |
|---|---|
| Отвечает на вопрос | Даёт ли плагин прирост на новых экземплярах той же семьи и когда он окупается |
| Сильные стороны | Дёшев, воспроизводим, годится как регрессионные ворота для каждого изменения harness'а; причинность читается напрямую |
| Слабые стороны | Не проверяет поток новых семей, рост библиотеки и поведение пользователя |
| Объём (оценка, не измерение) | 6 семей × 8 экземпляров × 3 попытки × 5 условий = 720 прогонов на модель-исполнителя, плюс адаптация |

### 4.3 Кандидат B: поток внедрения

Имитация заказчика: семьи приходят по одной, пользователь описывает каждую коротко и неполно (как в WorkBuddy-Bench, где запрос намеренно недоопределён), экземпляры разных семей перемежаются, в середине потока у части семей происходит сдвиг. Рядом идёт двойник без состояния; прирост считается как в CL-Bench: g_t = r(с состоянием) − r(без состояния) на том же экземпляре. Эпизоды размечены ролями PAST-Bench: cold, learn, evaluation, control.

| | |
|---|---|
| Отвечает на вопрос | Правда ли, что harness не приходится переписывать руками под каждую новую задачу; как он ведёт себя при 1, 5, 20 плагинах и при сдвиге |
| Дополнительные метрики | Кривая обучения по номеру экземпляра; число экземпляров до устойчивого успеха; интерференция; доля замеченных сдвигов; вмешательства человека на семью |
| Сильные стороны | Ближе всего к обещанию продукта; единственный вариант с осмысленным счётом вмешательств |
| Слабые стороны | Дорог; чувствителен к порядку (нужно не меньше трёх порядков); атрибуция сложнее; качество симулированного пользователя влияет на результат |

### 4.4 Кандидат C: матрица «автор × исполнитель × форма рельсов»

3–4 семьи, зато варьируется форма плагина: L0 ничего; L1 memory-файл; L2 только инструкции; L3 инструкции и скрипты; L4 скомпилированный workflow с ограниченными вызовами модели. По второй оси — автор (локальная модель, фронтирная, человек), по третьей — исполнитель (локальная, фронтирная).

| | |
|---|---|
| Отвечает на вопрос | Из чего должен состоять плагин и когда компилировать; нужен ли сильный автор, если исполнитель локальный |
| Сильные стороны | Прямо проверяет вывод раздела 2.4 на наших задачах; даёт точки окупаемости по каждому уровню |
| Слабые стороны | Не оценивает продукт целиком; полная матрица 5 × 3 × 2 велика, придётся брать срез |

### 4.5 Как их сочетать

Кандидаты не исключают друг друга. A — постоянные ворота; уровни L0–L4 из C можно добавить в A как абляцию на двух-трёх семьях; B — приёмочный прогон перед поставкой заказчику. Если нужен один, начинать с A: без него результаты B нельзя будет объяснить.

## 5. Не проверено и открытые вопросы

**Не проверено в этой сессии:**

- Hyperagents: прочитана первая половина текста через ar5iv; использованные модели не установлены.
- Ouroboros: прочитана часть статьи; репозиторий не открывался; ранние инциденты известны по блогу.
- ReasoningBank, SkillCraft, AFTER, PAST-Bench, SkillGLoW, MetaSkill-Evolve, Continual Harness, TTHE, MASA, HEXIS, TraceCompiler: аннотации и отдельные фрагменты, не полные тексты.
- Цифры по безопасности skills, OfficeQA, OdysseyBench, GDPval, скорость Qwen на DGX Spark: вторичные источники.
- «Meta Context Engineering» (MCE) и работы HCL и HSI упомянуты в Meta-Harness и Harness², сами не найдены.
- Разбиение held-in / held-out на Terminal-Bench 2.0 в Self-Harness (примерно 43 и 21 задача) выведено из процентов, в статье не названо.
- Лицензии и условия доступа к наборам данных, кроме SkillLearnBench и Harness².
- Аффилиации авторов Meta-Harness и AutoHarness указаны по репозиторию и по памяти.

**Открытые вопросы:**
